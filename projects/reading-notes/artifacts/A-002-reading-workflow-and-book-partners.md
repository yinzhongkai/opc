## 角色与逐书成员

| 参与者 | 工作范围 | 主要产出 |
|---|---|---|
| 用户 | 提出领域、阅读目的和偏好，选定书籍，表达感悟与判断，确认最终整理内容 | 阅读意图、选书结果、个人感悟与确认反馈 |
| 书目推荐官 | 根据用户目标和基础研究候选书，核实书目信息、比较适配程度与阅读顺序，维护荐书记录和书目入口 | 候选书单、推荐依据、阅读顺序建议、业务书目索引 |
| 每本书的阅读伙伴 | 围绕该书已读内容与用户讨论，整理讨论记录与个人笔记，读后根据历次讨论归纳总结 | 逐书档案、讨论记录、个人笔记、读后总结 |
| 项目经理 | 在已确认范围内协调阅读任务、输入依赖、进展与交付，维护 OPC 治理记录 | 计划、任务、决定、状态与成果索引 |
| 框架超级管理员 | 按用户授权定义或配置角色、技能、成员、工作区和会话 | 经核对的配置及成员初始化入口 |

书目推荐官建议设置一名项目成员。每一本选入项目、准备阅读的书设置一名独立阅读伙伴成员，贯穿该书的讨论与总结；候选书单中的未选书籍无需提前创建伙伴。阅读伙伴共用同一角色定义，通过不同成员 ID 和 scope 区分书籍。

用户界面和启动说明采用“《完整书名》阅读伙伴”。成员 ID 建议采用 reading-partner-<书名英文简称或拼音短名>，满足框架的小写字母、数字与短横线规范；书名后缀保持稳定，同名不同作者时增加作者后缀，必要时增加版本后缀。成员 scope 必须写明完整书名、作者、所用版本及对应讨论和归纳职责。

书目档案和索引记录“书名、作者、版本、书目编号、阅读伙伴成员 ID”的对应关系。书目编号辅助追踪，不代替按书名辨认伙伴。重读同一本书原则上沿用既有成员与档案，在内容中标注重读轮次；改变分工、版本基线或需要新成员时按实际授权处理。

以下是命名约定示例，不是已创建成员或已选择的书籍：

```text
角色：阅读伙伴
展示称呼：《书名甲》阅读伙伴
拟议成员 ID：reading-partner-shuming-jia
成员分工：负责《书名甲》（作者、版本）的阅读讨论、过程记录和读后归纳
```

本次不修改 TEAM 或成员文件，当前只有 project-manager 在册。当前共享角色目录没有同名的书目推荐官或阅读伙伴定义；现有研究员提供资料研究方法，作者提供写作整理方法，持续阅读讨论需要明确的专业职责。上述两个业务角色的共享定义、实际角色 ID 和有效技能由超级管理员在用户授权的配置工作中确定，不能仅凭称呼绑定身份。

建议配置方法覆盖荐书资料研究与事实核查、对话追问与观点比较、讨论记录及总结归纳。每个成员在原会话承担自身分工；每书会话由用户或获授权的超级管理员创建并初始化，项目经理不自行创建或派生。会话展示书名便于选择，实际绑定仍通过项目 ID、TEAM 和成员文件核对。仓库中的成员工作按单会话串行约定推进。

## 阅读流程

| 环节 | 主要行动人 | 输入与处理 | 输出或结束条件 |
|---|---|---|---|
| 提出方向 | 用户 | 说明领域与阅读目的；基础、语言、难度和时间偏好按需要补充 | 可据以选书的阅读意图 |
| 推荐书目 | 书目推荐官 | 核实候选书与版本，解释推荐理由、前置知识及阅读顺序；建议先给少量候选 | 有出处和取舍说明的推荐记录 |
| 选定书籍 | 用户 | 比较候选并选定书名和版本 | 选书结果、阅读目的；尚未明确的信息注明待补 |
| 开读准备 | 用户、超级管理员、对应阅读伙伴与项目经理按职责处理 | 配置并初始化该书成员，核实工作区与阅读材料；项目经理登记已授权阅读和归纳工作，伙伴建立逐书档案 | 书目、伙伴、材料与记录落点可核对，具备开读条件 |
| 阅读与讨论 | 用户和该书阅读伙伴 | 用户提出感悟或疑问；伙伴围绕所给章节或段落追问、比较观点、联系经验与证据 | 对应书目与出处的讨论记录 |
| 过程整理 | 该书阅读伙伴 | 把重要讨论归入主题，维护个人笔记和未解问题；章节结束或需要回顾时做简短阶段整理 | 阅读位置、讨论索引与重要感悟可继续接续 |
| 全书归纳 | 该书阅读伙伴 | 用户确认读完后，回读该书全部已保存讨论和笔记，按主题与理解变化归纳 | 含讨论引用、分歧及未解问题的读后总结候选稿 |
| 确认与归档 | 用户、伙伴和项目经理按职责处理 | 用户核对自己的观点表达，伙伴处理反馈；完成相应版本验证与记录 | 可追溯的读后总结与成果引用，后续阅读建议按需求再安排 |

阅读进度、材料版本和已读范围保持明确。伙伴缺少原文时可讨论用户提供的感悟，涉及作者原意的主张注明核实状态；不能凭书名宣称已读全书。需要补充材料时说明具体缺口。讨论以理解和思考为中心，记录正文不必搬入项目台账的治理字段。

每次讨论的关键内容及时落入逐书记录；聊天是交流入口，已保存的讨论材料是后续接续与归纳的依据。重要原话可按需要保留，详细对话原文仅在确有需要时保存。个人感悟归属用户，伙伴补充的解释单独标明，未达成的结论保留为疑问或分歧。

任务按一本书或一个可检查的阅读阶段组织；逐条感悟不用新建项目任务。最终总结明确引用已覆盖的讨论记录，资料缺失时说明缺失范围。用户的“已读”表示阅读状态，最终总结是否确认、任务是否完成仍依据对应完成条件。

## 笔记组织方式

采用“推荐记录集中保存、每本书独立归档、主题关联按需增加”的组织方式。书目档案负责导航与进度，讨论记录保存问题和观点形成的过程，个人笔记提炼用户希望长期保留的理解，读后总结呈现整本书的思考收获。

以下目录是工作区结构提案，业务目录和正式模板尚未创建：

```text
reading-notes-content/
  README.md                          阅读入口与全项目书目索引
  recommendations/
    <领域或阅读问题>/
      recommendation.md              推荐理由、依据与选书结果
  books/
    <书名简称>/
      README.md                      书目档案、伙伴、进度与讨论索引
      notes.md                       用户的重要感悟与个人笔记
      discussions/
        001-<主题简称>.md             一次讨论的关键内容与出处
        002-<主题简称>.md
      summary.md                     读完全书后形成的归纳总结
      assets/                        该书所需附件
  topics/                            按需形成的跨书主题入口
  templates/                         荐书、书目档案、讨论、总结模板
  exports/                           按需生成的分享或打印版本
```

书籍目录使用可辨认且稳定的书名简称；同名不同作者用作者后缀区分。讨论文件按书内顺序编号，日期、主题和阅读位置写入正文，便于总结引用与顺序回顾。读后总结在实际形成时再创建，未读完期间可以通过书目档案中的讨论索引和未解问题继续阅读。

个人笔记保留用户想长期使用的判断，并链接到讨论过程；读后总结链接到相关笔记和讨论。章节复杂或 notes.md 过长时再拆分子文件，保留档案入口。跨书主题入口只链接或比较相关材料，具体维护工作须另有对应成员范围与任务授权，不把某书伙伴自动扩展为全项目内容负责人。

## 内容格式

正文使用 UTF-8 Markdown，采用标题、列表、引用与普通相对链接。Markdown 是结构化文档的纯文本格式；少用编辑器专用语法有利于迁移和不同工具间使用。[CommonMark 规范](https://spec.commonmark.org/spec)

下列格式是候选约定，正式模板在声明并获授权的成果物工作区中创建。

### 推荐记录

- 阅读需求：领域或问题、阅读目的、已有基础、重要偏好。
- 候选书：完整书名、作者、语言、所推荐的版本或译本。
- 推荐理由：与用户目标的关系、主要覆盖内容、难度与前置知识、局限。
- 选择建议：推荐先读哪本，后续书目如何衔接。
- 核查依据：出版社、作者资料或可靠目录等来源链接与核对日期；事实与推荐判断分开。
- 选书结果：用户实际选定的书名、版本和理由；未选择时明确待选。

### 书目档案

- 书名、作者、译者、版本与阅读媒介。
- 书目编号、实际阅读伙伴成员 ID 与书名对应关系。
- 阅读目的、最想理解的问题、开始时的看法。
- 阅读状态：计划读、在读、暂停或已读；当前章节或位置。
- 讨论索引、未解问题、个人笔记入口、已形成的总结入口。
- 材料和来源位置；未知版本或缺失原文明确标注。

### 讨论记录

```markdown
# 讨论主题

- 日期：
- 书名及版本：
- 阅读位置与依据：章节、页码、电子书位置或用户提供的段落
- 阅读伙伴：实际成员 ID

## 我的感悟或疑问

记录用户原话，或注明是对用户表达的转述。

## 讨论内容

分别写清用户的想法、伙伴的回应与补充依据。
作者观点或摘录注明出处，尚未核实的解释明确标注。

## 本次收获

记录新的理解、发生变化的判断或暂时形成的结论。

## 尚未解决的问题

保留疑问、分歧和需要后续阅读验证的内容。
```

最小讨论记录只需能定位出处、表达用户的问题或感悟、保留关键回应及仍待解决的事项。按讨论内容调整篇幅，无需每次填写所有栏目。直接摘录与转述采用不同表达方式，电子书没有固定页码时使用章节和位置号，扫描 PDF 区分文件页码与印刷页码。

### 个人笔记

notes.md 按用户关注的主题整理：重要观点、自己的解释或例子、应用尝试，以及关联讨论。用户原始表达可以保留在讨论记录，个人笔记提炼长期使用的内容并链接回原处。由伙伴提出的想法标明来源，避免整理后变成未经用户表达或确认的个人判断。

### 读后总结

```markdown
# 《书名》读后总结

- 版本与材料范围：本次覆盖的讨论记录和个人笔记
- 整理人：该书阅读伙伴成员 ID
- 确认状态：待用户确认 / 已确认，并注明实际依据

## 最初的阅读问题及现在的回答

## 主要讨论主题与收获

每个主题引用相应讨论记录，区分作者观点、用户理解与伙伴补充。

## 我的理解如何变化

说明起初的看法、促成变化的讨论以及当前判断。

## 分歧与未解问题

## 值得保留的应用或后续阅读方向
```

读后总结以该书实际保存的历次讨论为输入，保留理解变化及未解决的分歧。原讨论记录保留，新的修订注明版本与变化；不能把遗漏的讨论、假设的感悟或伙伴推断补写成用户已经表达的事实。

## 成果物工作区

建议采用一个独立 Git 仓库容纳全项目的荐书记录与逐书成果。每本书有独立成员和目录，统一仓库便于书目导航、关联阅读及版本管理，成员 scope 决定实际维护范围。

| 事项 | 建议 |
|---|---|
| 工作区驱动 | git |
| 默认相对位置 | ../reading-notes-content |
| 本机拟议路径 | C:/Users/YinZh/Documents/workspace/reading-notes-content |
| 日常主线 | main |
| 仓库身份 | 启用前确认可核实的 repository 标识，当前待确定 |
| 精确基线 | 由实际初始化和验证后的完整 Git 提交确定，当前不填占位哈希 |
| 备份 | 建议先本地使用；是否增加私有远程备份由用户另行确定 |
| 编辑器 | 沿用支持 Markdown 的编辑器；正文不依赖专用插件 |

Git 可先初始化本地仓库，远程托管不构成开始使用的必要条件。Git 本地提交记录修改历史，异地备份另行安排。[Git 官方 git-init 文档](https://git-scm.com/docs/git-init)

当前 WORKSPACE 为 none，上述路径与参数只是提案。启用前由用户确认实际仓库和路径并授权操作；超级管理员填写 WORKSPACE，核对 repository、branch、完整 revision 与 checkout。真实仓库、基线和权限未明确时保持 none。submodule 会增加父子仓库操作，repo 面向多仓库管理，当前规模采用独立 git 更合适。

工作区保存荐书记录、逐书档案、讨论、个人笔记、总结、附件、正式模板及导出物。OPC 保存方案、成员与工作区声明、任务、决定、状态、评审和验收等治理成果，索引通过“成果物仓库 + 仓库内路径 + 精确最终合并提交”引用业务成果。边界依据 [配置规范](../../../CONFIG_SCHEMA.md) 与 [项目运行协议](../../../PROJECT_PROTOCOL.md)。

业务内容按根 [分支策略](../../../BRANCH_STRATEGY.md) 在相应 feature 或 bugfix 分支处理，按书或可交付阶段验证、合并并登记版本；一轮合并、验证和清理完成后再开始下一轮。工作区配置与业务内容分开处理。多本书的阅读可以交替进行，仓库会话执行仍由用户依次启动和停止。

## 启用顺序与确认事项

1. 用户确认 D-001 的阅读流程、逐书组织和内容格式，以及 D-002 的独立工作区方向；角色名称和每书独立伙伴已有 D-005 依据。
2. 用户授权超级管理员配置书目推荐官的角色、技能及成员，并创建、初始化其会话。领域荐书可在工作区启用前讨论，业务荐书文件保存须有已声明工作区。
3. 确定首批领域、书名与版本；按实际书名分别配置对应阅读伙伴，不预先建立未知书目的成员。
4. 用户确认真实仓库、路径与备份安排，授权超级管理员启用 WORKSPACE。实际业务内容写入前核对声明与 checkout，并在各自 scope 和任务授权内建立模板与逐书档案。
5. 按已授权的阅读与归纳任务启动各书阅读伙伴，保存过程记录；读后由对应伙伴总结，用户确认其个人观点表达与最终成果。

成员、会话和工作区可以按准备条件先后配置；业务成果保存以工作区已声明且可操作为前提。本轮只交付治理候选方案，具体成员配置与首批书目继续待确定。
