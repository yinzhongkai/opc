## 1. 结论

**结论：第一阶段在 Windows 桌面端技术条件下有条件可实现，建议进入算法原型和端到端垂直切片；不应在“卡点自然度”、素材边界和最低 Windows 版本尚未量化前直接承诺完整 MVP 的工期或效果。**

基础能力——本地媒体解码、镜头切换与运动强度提取、音频节拍/瞬态分析、事件时间线编辑、短音色触发、三类基础视觉渲染、项目保存和音视频导出——均有成熟工程路径。A-003 0.1 也证明同类桌面软件可以完成桌面音频、图形视觉、项目恢复和 FFmpeg 导出，但其实现、素材、协议和品牌不属于本项目可复用来源。

主要不确定性不是“能否生成结果”，而是生成的节奏是否对目标用户足够自然、不同素材下是否稳定，以及预览与导出能否保持严格同步。这三项必须由代表性素材、盲评口径和基准硬件验证，不能仅凭静态设计宣告通过。

| 能力 | 可行性 | 判断与条件 |
|---|---|---|
| 独立桌面工作区、时间线和事件编辑 | 高 | 常规桌面 UI 与状态管理问题；需把耗时分析、解码和导出移出 UI 线程。 |
| 镜头切换、显著运动检测 | 高 | 可先用直方图/结构差异、光流或块运动等可解释方法；需要代理帧和阈值归一化。 |
| 通用“动作落点”识别 | 中 | 简单素材可由运动峰值近似；复杂人物动作、运镜和特效会降低可靠性，必要时才引入本地模型。 |
| 视频事件生成短节奏音轨 | 高 | 事件到鼓点/打击乐/短合成音的映射和离线混音可控；音色许可必须明确。 |
| “卡点自然、有节奏感” | 中，条件性 | 属于主观质量目标；必须以样例集、人工修正量和盲评阈值作为放行门槛。 |
| 音频节拍、瞬态、响度与频段分析 | 高 | 成熟 DSP 路径；自由节奏、弱瞬态和噪声素材需要置信度及失败提示。 |
| 三类基础音频驱动视觉 | 高 | 波形/示波器、频谱几何、粒子/线条脉冲均可由统一事件与音频特征驱动。 |
| 预览、音轨和视频导出 | 中高 | 媒体管线成熟，但容器/编码器、硬件差异、许可和精确时间戳必须专项验证。 |
| 项目保存、重开和异常恢复 | 高 | 采用版本化项目格式、原子保存、自动保存与可重建缓存即可实现。 |
| Windows 安装与可信分发 | 高（有门槛） | 目标平台和 x64 架构已收敛；仍需冻结最低系统版本、编译器、编码器、签名和安装器，并在干净系统验证。 |

架构放行建议为 **Go with gates**：允许开展技术原型和垂直切片；只有第 9 节 G1～G4 的证据达到约定阈值后，才进入完整 MVP 排期或对外承诺。

## 2. 设计依据、假设与边界

### 2.1 已确认依据

- 首发形态是独立桌面应用。
- 主路径是视频生成可编辑节奏音轨；音频生成少量视觉模板为配套路径。
- 两条路径共用节奏事件时间线。
- 一期只生成鼓点、打击乐或短合成音，不生成完整歌曲。
- 一期不包含 VST3、Blender/GPLA、复杂效果链、专业合成器或现场演出集成。
- 项目保存、异常恢复、预览/导出一致性、失败反馈和可信分发属于 P0，而非后置优化。
- 界面层采用 Qt Quick/QML；QML 负责视图、布局、状态绑定和交互，Qt/C++ 负责模型、ViewModel 和应用服务。
- 算法核心采用 C/C++ 实现，并与 Qt 界面类型隔离。

### 2.2 工程假设

- P0 以**本地离线处理**作为可独立交付的基线；云端增强只保留扩展边界，未经后续确认不成为依赖。
- 导入素材只读，系统不得修改原始文件；代理、波形、特征和导出中间文件写入项目缓存。
- 首版以 CPU 可运行作为兜底；GPU 或专用推理后端属于可选加速，不能成为项目可打开、编辑或导出的唯一条件。
- 为形成原型基准，建议先用不超过 5 分钟、1920×1080、30 fps 的 H.264/AAC MP4 与 WAV/PCM 作为工程样例；这是待产品确认的测试起点，不是已批准的最终格式或素材上限。
- 第一阶段只考虑 Windows x64 桌面平台；不生成 x86、ARM64 或 ARM64EC 产物，Linux 不进入本阶段的设计目标、构建预设、CI、安装包、兼容性矩阵或验收范围。最低 Windows 版本及基准硬件尚未确认。

### 2.3 明确非目标

- 不复刻或链接参考安装包中的闭源代码、素材、协议或品牌资产。
- 不在一期提供脚本执行环境、插件宿主、共享纹理、直播输入、实时演出或多人云协作。
- 不把动作语义理解、完整音乐生成或任意素材“零人工修正”作为一期技术承诺。
- 本文不决定商业许可策略，不替代代码签名、编解码器专利/许可证和音色素材授权审查。

## 3. 建议系统边界与架构

```text
本地媒体文件
    │
    ▼
媒体探测/解码 ──► 代理帧、波形、媒体时间映射
    │                         │
    ├─► 视频分析 worker ─────┤
    └─► 音频分析 worker ─────┤
                              ▼
                    事件融合与节奏时间线
                      │       │       │
                      │       │       └─► 项目存储/自动恢复
                      │       └─► 音色分配与音轨渲染
                      └─► 视觉模板渲染
                                  │
                     预览协调器 ──┴── 导出协调器
                                          │
                                   WAV / 视频文件
```

### 3.1 模块职责

| 模块 | 单一职责 | 失败边界 |
|---|---|---|
| Desktop Shell | 窗口、命令、时间线交互、参数面板和可访问错误提示 | 不执行长时解码、分析或导出；worker 失败不得终止 UI。 |
| Project Store | 版本化项目文档、原子保存、自动保存、迁移和素材重定位 | 缓存损坏可重建；项目主文档损坏时提供最近一次可验证自动保存。 |
| Media Service | 探测流、解码、缩略图/代理、波形、PTS 映射和只读素材访问 | 损坏/不支持媒体返回结构化错误，不把部分解码伪装为成功。 |
| Video Analysis Worker | 镜头、运动、候选动作峰值及置信度 | 可取消、可重试、资源受限；崩溃只影响当前作业。 |
| Audio Analysis Worker | 节拍、瞬态、响度、频带能量及置信度 | 无明显节奏时返回低置信度和原因，不能捏造稳定 BPM。 |
| Event Engine | 事件归一化、融合、密度/偏移、重分析合并和锁定保护 | 结果按分析版本提交，取消/失败不得留下半更新事件集。 |
| Audio Renderer | 音色分配、试听、混音和独立音轨渲染 | 缺少音色或写出失败时不覆盖已有导出。 |
| Visual Renderer | 三类模板、参数驱动、离屏与屏上统一渲染 | GPU 不可用时报告能力或使用已验证的软件/兼容路径。 |
| Preview Coordinator | 播放头、媒体、事件、音频和视觉的同步预览 | 允许降级画质或代理分辨率，不改变规范时间线。 |
| Export Coordinator | 固定时间线修订、逐帧渲染、编码、封装、进度和取消 | 写临时输出，成功后原子替换目标；失败清理临时文件。 |
| Distribution & Diagnostics | 依赖清单、完整性、签名、日志和崩溃信息 | 默认不上传素材或遥测；任何联网行为需显式同意。 |

### 3.2 已确认技术基线与候选细节

- **已确认界面基线**：界面层使用 Qt Quick/QML，第一阶段只交付 Windows x64 版本。常规控件与布局使用 Qt Quick Controls；高密度时间线、波形和视觉预览通过 C++ 自定义 `QQuickItem` 接入场景图。Qt minor 版本及开源/商业许可证路径尚未决定；选定版本时必须核对最低 Windows 版本和官方支持矩阵。[Qt 支持平台](https://doc.qt.io/qt-6/supported-platforms.html)
- **已确认 Qt 供应基线**：不使用 Qt 预编译二进制包，从固定版本的官方源码自行构建。源码、构建和安装目录必须分离且使用短路径；保存源码版本/哈希、编译器与 SDK 版本、完整 configure 参数、配置摘要和产物清单。Qt 官方要求 Windows 源码构建环境预先具备受支持编译器、CMake 3.22+、Ninja 和 Python 3；源码本身不能替代编译器。[Qt Windows 源码构建](https://doc.qt.io/qt-6/windows-building.html) [Qt Configure](https://doc.qt.io/qt-6/configure-options.html)
- **已确认算法基线**：媒体分析、事件融合、音频生成和其他算法核心使用 C/C++。建议以现代 C++ 组织业务对象、资源生命周期和并发任务，仅在第三方库接入、跨进程/插件 ABI 或性能证据要求时提供窄 C 接口；C++ 标准与最终编译器仍待 D-003/D-006 确认。
- 媒体管线候选：固定版本并随应用本地部署的 FFmpeg 库，用 API 完成探测、解码、重采样、编码和封装，不拼接 shell 命令。FFmpeg 官方文档分别提供 codec、format、filter、scale 和 resample 库接口。[FFmpeg 文档](https://ffmpeg.org/documentation.html)
- 视频基线算法候选：OpenCV 的帧差、特征和光流能力；先用可解释算法建立基线，再判断是否需要学习模型。[OpenCV Optical Flow](https://docs.opencv.org/4.x/d7/d8b/tutorial_py_lucas_kanade.html)
- 可选模型运行时：只有传统方法无法达到 G1 质量门槛时，才评估 ONNX Runtime 的本地 C++ 推理；模型、执行后端、包体和许可需单独评审。[ONNX Runtime C++](https://onnxruntime.ai/docs/get-started/with-cpp.html)
- 渲染候选：Qt Quick Scene Graph/Qt RHI 上的自定义渲染节点，屏上预览与离屏导出复用同一视觉参数和渲染核心；不可直接假设不同 GPU 后端像素完全一致。

Qt Quick/QML 和 C/C++ 是 D-002 已确认基线；FFmpeg、OpenCV、ONNX Runtime、Qt 确切版本及其他第三方组件仍是候选细节。选型时必须同时比较许可证、二进制体积、硬件回退、调试能力、维护成本和 Windows 测试范围。替换已确认基线需由新决定明确替代 D-002，不能在实现中静默变更。

### 3.3 Qt 与 C/C++ 模块边界要求

- **TR-A-001 Qt Quick/QML 界面边界**：窗口、视图、布局、交互、快捷键、本地化和可访问提示放在 QML `ui` 层；Qt/C++ 提供注册类型、模型和 ViewModel。不得在 QML/JavaScript 中执行媒体解码、DSP、特征计算、模型推理、大数组循环或长时导出。
- **TR-A-002 C/C++ 算法核心**：视频分析、音频分析、事件融合和音轨生成实现为可脱离 GUI 运行及测试的 C/C++ 模块；核心库不得依赖 Qt Widgets、QML 或场景图类型。
- **TR-A-003 依赖方向**：允许 `ui -> application services -> algorithm/media core` 单向依赖；算法核心不得回调具体页面或持有 UI 对象。进度、结果、取消和错误通过接口/消息传递。
- **TR-A-004 跨边界数据**：公共契约使用定长整数、UTF-8 字符串、不可变值对象、显式数组长度和版本字段；Qt 的 `QString`、`QImage`、`QObject` 等类型只在适配层转换，不进入持久化 schema 或稳定算法 ABI。
- **TR-A-005 内存与线程所有权**：所有跨模块缓冲区明确创建方、释放方、只读/可写属性和生命周期；UI 只接收拥有明确生命周期的快照或句柄，worker 不跨线程直接访问 `QObject`。
- **TR-A-006 构建与测试**：采用 CMake 管理 Qt 源码构建以及应用、核心库、worker 和测试目标；Qt 采用 Windows x64 shadow build，源码、构建、安装目录分离，不使用 `-developer-build` 生成发布 SDK。每个目标固定语言标准、编译器/Windows SDK、运行时、警告策略和平台预设；Qt、应用和同进程原生依赖使用同一 C++ ABI。算法测试必须能在无图形界面的 Windows CI 中运行，Qt UI 测试与算法基准分开。

## 4. 核心数据与接口契约

### 4.1 统一时间契约

- 项目规范时间使用有符号 64 位整数纳秒 `timeNs`；不得以浮点秒数或单一视频帧号作为持久化真值。
- Media Service 必须保留源流 `PTS + time_base`，并提供源 PTS、`timeNs`、音频采样索引和输出帧号之间的显式转换。
- 视频帧事件以实际显示时间戳定位；可变帧率素材不得先假设恒定 fps。
- 音频混音以固定项目采样率和整数采样索引工作；采样率由项目格式保存，重开后不得静默改变。
- 预览和导出都读取同一个已提交的 `timelineRevision`；导出进行中编辑产生新修订，不得改变已开始作业的结果。

### 4.2 RhythmEvent 最小模型

| 字段 | 要求 |
|---|---|
| `id` | 项目内稳定唯一；人工编辑和锁定后重分析不得复用给另一事件。 |
| `timeNs` / `durationNs` | 规范时间；点事件的持续时间可为 0。 |
| `kind` | 至少区分 `shot`、`motion_peak`、`action_peak`、`beat`、`onset`、`band_energy`、`manual`。 |
| `source` | 产生事件的素材流、算法/用户、算法版本和参数摘要。 |
| `strength` | 归一化到 `[0,1]`，并说明归一化作用域；不同算法的值不可未经标定直接比较。 |
| `confidence` | `[0,1]` 或 `not_applicable`；人工事件不可伪造模型置信度。 |
| `locked` | 用户锁定状态；锁定事件的位置、类型和用户属性受重分析保护。 |
| `userEdited` | 标识用户是否移动、改型或改强度，用于合并和撤销。 |
| `analysisRevision` | 指向生成它的不可变分析结果版本。 |
| `soundAssignment` | 可选；音色 ID、增益、音高/变体和淡入淡出参数。 |

### 4.3 重分析合并规则

1. 新分析结果先写入临时修订，不直接修改当前时间线。
2. 当前范围内未锁定的自动事件可被新修订替换；人工事件和锁定事件完整保留。
3. 新事件与锁定事件落入同一可配置合并窗时，默认保留锁定事件，并记录新事件被吸收或抑制的来源。
4. 合并完成后以一次可撤销事务提交；失败或取消时当前修订保持不变。
5. 调整密度、阈值和整体偏移必须可预览；正式应用后进入撤销/重做历史。

### 4.4 项目与缓存契约

- 项目主文档保存 `schemaVersion`、素材引用与指纹、流信息、时间基准、事件、轨道、视觉/音色参数、导出配方和应用版本。
- 素材引用同时保存可重定位路径、文件大小和内容指纹；路径失效时提示定位，不自动关联同名不同内容文件。
- 项目主文档、自动保存和用户预设为持久数据；代理、缩略图、特征和临时渲染为可删除、可重建缓存。
- 保存采用“临时文件写完并校验后原子替换”；保留最近一次成功自动保存及正常退出标记。
- 项目格式必须提供向前迁移器；未知新字段应按兼容策略保留或明确拒绝，不能静默丢失。

### 4.5 作业与错误契约

- 分析、代理生成和导出作业具有 `jobId`、输入指纹、参数摘要、状态、进度、取消令牌、日志位置和结果修订。
- 相同输入与参数的重复请求应复用已验证缓存，或产生等价结果；不得并发覆盖同一输出。
- 错误至少分类为 `unsupported_media`、`corrupt_media`、`resource_limit`、`analysis_low_confidence`、`decode_failed`、`render_failed`、`encode_failed`、`permission_denied`、`dependency_integrity_failed` 和 `cancelled`。
- 用户提示包含失败阶段、是否保留当前项目、可执行的恢复建议和诊断 ID；日志不得默认包含媒体内容或用户目录之外的不必要隐私数据。

## 5. P0 功能技术需求

以下 `TR-F-*` 均为第一阶段 P0，除非明确注明需要前置产品确认。

### 5.1 工作区、媒体与时间线

- **TR-F-001 媒体导入与探测**：系统必须只读导入本地音频或视频，读取容器、流、时长、分辨率、帧率/可变帧率、采样率、声道和旋转信息，并在不支持、损坏或受保护媒体上返回结构化错误。
- **TR-F-002 代理与波形**：系统必须流式生成可取消的代理帧、缩略图和音频波形；不得要求把完整视频一次性载入内存。缓存必须按素材指纹、算法版本和参数失效。
- **TR-F-003 同步工作区**：工作区必须包含媒体预览、波形、事件时间线、播放头和缩放；拖动、播放和定位均使用第 4.1 节时间契约。
- **TR-F-004 事件编辑**：用户必须能够增删、移动、选择、锁定事件，修改强度/类型/音色分配，执行吸附、整体偏移、撤销和重做；所有修改形成可回滚事务。

### 5.2 视频到节奏音频主路径

- **TR-F-005 视频候选事件**：视频分析必须分别输出镜头切换、显著运动峰值和候选动作落点，不得只输出无法解释的单一综合分数；每项携带来源、强度、置信度和分析版本。
- **TR-F-006 事件融合**：Event Engine 必须按可配置权重、最小间隔、密度和合并窗产生规范事件集；参数变化和算法升级可重现，结果必须能追踪回原始候选。
- **TR-F-007 锁定保护**：重新分析、密度调整或阈值变化不得覆盖人工事件和锁定事件，合并行为符合第 4.3 节。
- **TR-F-008 节奏音色映射**：系统必须支持不超过三组一期音色，把事件类型/强度映射为鼓点、打击乐或短合成音；用户可替换单个声音并试听。所有随包音色必须有可分发许可证和来源记录。
- **TR-F-009 音轨渲染**：系统必须从固定 `timelineRevision` 生成可独立播放的音轨，处理峰值、削波、重叠和尾音；导出前提供峰值或削波告警，不得静默产生损坏音频。

### 5.3 音频到视觉配套路径

- **TR-F-010 音频特征**：音频分析必须输出节拍、瞬态、响度和频段能量；对自由节奏、弱瞬态或噪声素材给出置信度和失败原因，不强制捏造固定 BPM。
- **TR-F-011 三类视觉模板**：系统必须提供波形/示波器、频谱几何、粒子或线条脉冲三类模板，并至少支持灵敏度、密度、强度和整体偏移；模板使用规范时间和同一事件集驱动。
- **TR-F-012 统一渲染配方**：屏上预览与离屏导出必须共享视觉参数、随机种子、事件修订和渲染配方；实现允许使用不同 GPU 后端，但输出时序不得分叉。

### 5.4 保存、恢复、导出与失败反馈

- **TR-F-013 项目生命周期**：系统必须支持新建、保存、另存、重新打开、素材重定位、自动保存和异常退出恢复提示；重开后恢复素材引用、事件、锁定状态、模板、音色和用户参数。
- **TR-F-014 导出**：系统必须支持独立节奏音轨、带原音频的视觉视频和合成卡点视频；具体容器/编码器矩阵由待确认项 O-003 决定，最小原型需覆盖 WAV/PCM 与 H.264/AAC MP4。
- **TR-F-015 导出事务**：导出写入临时目标，成功校验后再提交；用户取消、磁盘不足、编码失败或应用异常不得覆盖已有文件，并应清理或标识可恢复临时文件。
- **TR-F-016 进度和诊断**：代理、分析和导出必须展示阶段、进度、取消入口和可行动错误；低质量结果必须标注“需要人工调整”，不能包装成成功的自动卡点。
- **TR-F-017 外部依赖**：编解码器、模型和其他可执行依赖必须固定版本、随包或通过受控安装提供，并记录来源、许可证和完整性；应用不得在未提示和未获同意时联网下载或执行组件。
- **TR-F-018 可验证分发**：正式安装包和可执行文件必须具备平台可验证的发布者身份；依赖安装到应用私有目录，不覆盖系统共享 DLL，发布物提供版本、哈希、许可证清单和软件物料清单。

## 6. 质量属性技术需求

- **TR-Q-001 时序正确性**：同一导出配方下，预览可见事件与导出视频中的事件位置误差不得超过一个输出视频帧；音轨起止时间与视频时间线使用同一零点，测试覆盖恒定和可变帧率素材。
- **TR-Q-002 确定性**：给定相同素材指纹、算法版本、参数、随机种子和平台，事件集合及离线音频结果必须可复现；允许的渲染像素差异需由跨 GPU 容差定义。
- **TR-Q-003 交互响应**：文件分析、代理和导出不得阻塞 UI 线程；事件增删、移动、锁定、撤销和播放控制在约定基准硬件上应保持即时反馈。P95 延迟阈值须在确认基准硬件后写入测试计划。
- **TR-Q-004 性能与规模**：解码和分析必须流式或分块执行，设置内存、磁盘缓存、线程和并发作业上限；在 O-002 素材上限与 O-004 基准硬件确认后，分别量化首次预览、分析完成和导出耗时。
- **TR-Q-005 可靠性**：作业取消、worker 崩溃、磁盘不足、素材丢失和项目迁移失败不得破坏最近一次成功保存；自动恢复必须说明恢复来源和时间，不静默回滚。
- **TR-Q-006 安全与隐私**：把媒体当作不可信输入；解码/分析 worker 使用最小权限和资源限制，所有路径通过参数 API 传递而非 shell 拼接。P0 默认离线，不上传素材、特征或崩溃附件。
- **TR-Q-007 供应链**：构建固定第三方依赖版本，生成许可证和 SBOM，校验下载物；Windows 发布执行代码签名、恶意软件扫描、依赖清单和干净系统安装/卸载验证。
- **TR-Q-008 Windows 兼容性**：核心项目格式、事件契约和算法结果与 UI 框架及 Windows UI 类型解耦；在所有已承诺 Windows 版本上复用相同 schema 和黄金样例。GPU、音频设备、媒体编码器和缩放比例差异必须在能力矩阵中显式记录。本阶段不以 Linux 可编译或可运行作为验收条件。
- **TR-Q-009 可维护性**：媒体、分析、事件、渲染和项目模块通过版本化接口隔离；算法参数及版本进入项目与诊断记录，模型或算法升级不得不可追踪地改变旧项目。
- **TR-Q-010 可测试性**：每个分析器提供确定性样例、边界输入和基准数据；时间映射、锁定合并、原子保存和导出事务具备自动化测试，端到端黄金样例比较事件、音频峰值和帧时间戳。

## 9. 验证门槛

### G0：验收输入就绪

由用户/产品侧确认或提供：代表性视频与音频样例、最低 Windows 版本与基准硬件、典型/最大素材边界、允许的人工修正量、“卡点自然”评分方法与通过阈值、音色及视觉默认风格；构建侧须先确认 D-006 编译器路线。缺少这些信息不阻止算法概念验证，但缺少编译器会阻止 Qt 和应用构建，其他缺口则阻止宣告产品效果和性能验收通过。

### G1：算法可行性原型

- 覆盖稳定节拍、自由节奏、快切、慢镜头、近乎静止、显著运镜和动作落点等样例类别。
- 输出镜头、运动、动作候选及来源/置信度；能够生成可试听节奏轨。
- 记录分析时间、事件密度、人工增删/移动数量和盲评分。
- 通过条件使用 G0 确认的阈值；若未确认，只能报告测量结果，不能写“自然度通过”。

### G2：端到端垂直切片

- 完成“导入视频 → 分析 → 编辑/锁定 → 试听 → 保存/重开 → 导出音轨和合成视频”。
- 重新分析保持锁定和人工事件；撤销/重做、取消和失败不破坏当前修订。
- 使用相同 `timelineRevision` 验证预览与导出位置误差不超过一个输出帧。

### G3：配套视觉与可靠性

- 完成音频特征及三类视觉的最小代表实现，验证屏上/离屏使用同一配方。
- 覆盖损坏媒体、无明显节奏、近乎静止、素材丢失、磁盘不足、worker 崩溃和异常退出恢复。
- 在确认的素材上限与基准硬件上记录内存、缓存、首次预览、分析和导出性能。

### G4：Windows 兼容与可信分发

- 在每个已承诺 Windows 版本的干净环境验证安装、首次启动、导入、预览、保存、导出、升级和卸载。
- 验证无隐式网络下载、应用私有依赖、发布签名、哈希、许可证与 SBOM。
- 编解码格式矩阵、GPU/软件路径和已知限制随发布物固定并可复核。

O-001 的平台顺序已由 D-004 解决为“第一阶段只考虑 Windows”，CPU 架构已由 D-005 解决为 x64；最低 Windows 版本和基准硬件继续作为 G0 输入，不恢复 Linux、x86 或 ARM64 范围。表中其余待确认项不改变 D-001、D-004 与 D-005 的已确认方向；它们是把候选验收标准转换为可量化工程门槛所需的输入。

## 11. 建议实施顺序

1. 先做 G0/G1：用离线脚本或最小 worker 验证镜头、运动、动作峰值、融合和节奏试听，不先投入完整 UI。
2. 再做 G2：建立规范时间、事件模型和项目格式，打通主路径垂直切片；这一阶段冻结核心契约。
3. G2 通过后做 G3：补齐音频到视觉、自动保存、异常恢复和资源边界。
4. 最后做 G4：冻结实际依赖与格式矩阵，在已承诺 Windows 版本上完成签名、许可证、安装和发布验证。

若 G1 未达到已确认的自然度/修正量门槛，应先判断问题来自事件检测、融合规则、音色映射还是评分口径。只有证据表明可解释算法已到瓶颈时，才进入本地模型方案评估；不得用扩大到完整音乐生成来掩盖主路径尚未验证。

## 12. 自查结论

- 已覆盖 A-002 0.2 的全部 P0 能力，并通过第 7 节建立追踪关系。
- 已把已确认范围、工程假设、候选选型和待产品确认项分开；未把未知容量或自然度指标伪造成事实。
- 已定义预览/导出统一时间、事件锁定、重分析、项目恢复、作业失败和外部依赖等关键契约。
- 已保留 CPU/本地离线基线与清晰的平台隔离边界；第一阶段不承担 Linux 交付，同时未把云端、模型、VST3、Blender 或参考产品实现引入一期必需范围。
- 已按 D-002/D-005 固定 Qt Quick/QML、C/C++、Windows x64 与 Qt 源码构建基线，并通过 TR-A-001～006 防止算法被 UI 类型、线程、内存所有权或不一致 ABI 耦合；编译器按 D-006、Qt 具体版本及许可证路径仍显式待定。
- 本文可作为研发原型与后续测试计划的输入，但仍为 draft；最低 Windows 版本、格式、性能与自然度阈值需按第 10 节和 G0 确认。
