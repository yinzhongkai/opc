# 成员、岗位与专业知识：项目会话模板

你创建项目和成员会话，会话读取岗位职责、所需专业知识与项目资料，按成员分工开展工作。模板以成员、岗位和专业知识为核心，适用于软件开发、旅行规划、图书写作等项目。专业知识保存在 `knowledge/`，采用平铺的普通 Markdown 文档。

## 核心关系

- 成员：项目中的具体身份，一个成员对应一个岗位；成员的 `scope` 描述本项目负责哪部分。
- 岗位：共同职责、工作边界、预期产出与基础知识要求，保存在共享 `roles/`。
- 专业知识：完成工作所需的知识、方法和判断依据，保存在共享 `knowledge/`，按 ID 引用。

岗位按职责划分。专业方向在项目组建时配置；同岗位人数和工作区域的差异由成员名单表达。

```text
成员的岗位
  ├── 共享岗位职责与基础知识
  └── 本项目为该岗位补充的知识
                  ↓ 合并去重
         本项目该岗位的知识集合
                  ↓ 结合成员 scope 与项目约束
            当前成员的工作范围
```

同一项目、同一岗位的成员加载同一套知识，实际分工可以不同。软件项目中的前后端成员都使用 `developer` 岗位，分别负责界面与服务端。读取后端知识不意味着前端成员可以接管后端任务。

`knowledge/` 没有子目录，每个文件以其知识 ID 命名。这里的专业知识是普通资料，与平台原生 Skills 不同。会话初始化由 `AGENTS.md` 引导至公共协议。

`projects/` 当前仅保留[太空律动](projects/space-rhythm/PROJECT.md)项目。原记账软件、日本旅行和图书写作三个示例项目已移除，可从 Git 历史恢复。使用时先确认项目目标与约束，再安排成员开展工作。

## 如何配置

共享岗位以 [project-manager.md](roles/project-manager.md) 为例，其文件头为：

```yaml
---
id: project-manager
name: 项目经理
status: active
knowledge: [project-management]
---
```

正文定义共同职责、边界与产出。这里的 `knowledge` 是基础知识，至少包含一个知识 ID。

项目的 [TEAM.yaml](projects/space-rhythm/TEAM.yaml) 同时保存岗位补充知识和成员名单。以下摘录组织管理员作为配置示例（scope 简写），完整成员以该文件为准：

```yaml
project: space-rhythm
managedBy: organization-manager-01
roleKnowledge: {}

members:
  - id: organization-manager-01
    role: organization-manager
    status: active
    scope: [成员与岗位知识配置、按需增员、初始化缺口跟踪]
```

`roleKnowledge` 是以共享岗位 ID 为键、补充知识 ID 列表为值的映射。未配置的岗位只使用基础知识；整个字段可以省略或写为 `{}`。补充项只能增加知识，不能移除基础知识或覆盖职责。

| 项目与岗位 | 基础知识 | 项目补充知识 |
|---|---|---|
| 软件项目的项目经理 | 项目管理 | 软件研发基础 |
| 旅行项目的项目经理 | 项目管理 | 旅行规划 |
| 软件项目的研发工程师 | 软件工程 | 前端开发、后端开发 |
| 旅行项目的规划师 | 方案规划 | 旅行规划 |
| 图书项目的规划师 | 方案规划 | 长篇写作 |

成员不单独配置知识。给项目补充某个岗位的知识时，会影响该项目使用该岗位的全部成员；其他项目的岗位组合不变。

## 项目共享文件

| 文件 | 用途与维护方式 |
|---|---|
| `AGENTS.md` | 项目身份和公共文件位置 |
| `PROJECT.md` | 目标、范围、交付物与具体约束；技术栈、日期、读者等写在这里 |
| `TEAM.yaml` | 成员、岗位补充知识、状态和分工，由组织管理员维护 |
| `STATUS.md` | 当前进展和阻塞，由项目经理汇总 |
| `TASKS.md` | 成员直接更新自己任务的状态、进展、产物和阻塞；项目经理维护负责人、依赖、优先级等计划信息 |
| `DECISIONS.md` | 已确认决定及待决定事项，保留确认来源 |
| `HANDOFFS.md` | 需要其他成员行动的请求、协调与工作交接 |
| `<项目目录>/artifacts/` | 正式产物，例如 `projects/space-rhythm/artifacts/`；软件源码位置另按项目约定确定 |

## 创建成员会话

让工具能访问模板目录及目标项目资料，新会话发送：

```text
项目：space-rhythm
成员：organization-manager-01
请按 SESSION_PROTOCOL.md 初始化，读取我的岗位基础知识和项目补充知识，
并汇报岗位、分工、实际读取的文件与当前任务。
```

如果显式填写岗位，这个成员的岗位是 `organization-manager`，基础知识为 `team-management`，当前无项目补充知识。只声明岗位且同岗位有多人时，需要补充成员 ID。项目和成员能唯一确定时，岗位从名单推导。

会话查找成员 → 读取岗位 → 合并基础与补充知识并读取正文 → 读取项目背景、任务、决定和交接 → 返回初始化回执。详细字段和失败处理以 [初始化协议](SESSION_PROTOCOL.md) 为准。

会话之间通过共享文件传递事实。成员完成一部分工作后，直接更新自己任务的进展和产物链接；项目经理调整任务计划并汇总项目状态。日常进展不需要重复写交接，只有需要其他成员行动、协调或接手时才记录交接。交接记录不会自动唤醒另一个会话，需要你进入对应会话继续工作。

## 动态调整团队

先以 `organization-manager-01` 创建组织管理员会话，然后可以说：“增加一名研发成员，负责数据导出页面”“给当前项目的项目经理补充旅行规划知识”“停用某成员，未完成任务交给项目经理重新分配”。

- 人数或分工变化：维护成员记录，复用现有岗位。
- 当前项目需要更多领域知识：修改本项目 `roleKnowledge`。
- 知识库缺少内容：新增一份平铺的知识文档，再引用其 ID。
- 共同职责确有区别：新增岗位。前后端、旅行或图书等专业方向本身不作为拆岗位的理由。
- 成员停用：`active → inactive`，直接停用并保留成员历史。未完成任务和成果保留，由项目经理重新分配；无需等待任务接收确认，也不能把任务自动标为完成。组织管理员停用前指定新的有效管理员。

组织管理员在用户已授权范围内维护配置。修改共享岗位或知识正文时检查所有项目引用，说明影响；尚未授权的共享变更先提出方案。修改项目组合与修改公共知识正文的影响范围不同。

## 平台与复用

参见 [Codex 说明](adapters/codex/README.md) 和 [Kimi Work 说明](adapters/kimi/README.md)。知识文件是供会话读取的普通资料，不负责安装工具、授予权限或执行任务。实际能力通过任务成果验证。

多个项目共享一套岗位库和知识库，只维护各自的项目目录。资料同步和版本一致性由用户通过 Git 管理；会话读取并写回当前可访问的项目文件。聊天内容不会自动成为其他成员可见的项目事实。
