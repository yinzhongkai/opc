### 10.1 镜像总装：WIC 还是自定义打包

#### 10.1.1 阿凯的提议与达哥的反问

阿凯做过功课："我翻了官方文档，做烧写镜像那节全是 WIC 打头——构建完出一个能直接 `dd` 进 SD 卡的整镜像。我们的 NAND 整镜像，是不是也该用它？"

"问题问反了。"达哥说，"不是'该不该用'，是'能不能用'。先把它干什么活、按什么模型干活搞清楚，再回来对 tiger 的存储形态。"

#### 10.1.2 WIC 与 IMAGE_BOOT_FILES：块设备世界的工具

阿凯翻完文档回来，给这个工具上户口——它此前只在 chapter 3 的目录清单里露过一面，今天首次正式引入：**WIC**——Yocto 的磁盘镜像创建工具（OpenEmbedded Image Creator），按一份 `.wks` 分区描述，把内核、dtb、rootfs 等构建产物摆进一张带分区表的磁盘镜像。

配套变量一并正式引入：**镜像启动文件（IMAGE_BOOT_FILES）**——BitBake 变量，声明 WIC 制作镜像时拷贝进启动分区的文件列表（内核、dtb、boot.scr 之类）。

关键是工作模型：WIC 眼里的世界是**块设备**——镜像开头一张分区表（GPT 或 MBR，分区表的两种格式），启动分区格 FAT、根分区格 ext4。对 tiger 逐条过：

| WIC 的前提 | tiger 的现实 |
|-----------|-------------|
| 介质是块设备，开头画 GPT/MBR 分区表 | 裸 NAND，分区表在 dts 里（9.6.2），介质开头是 BL1 |
| 启动分区格 FAT，U-Boot 从 FAT 读文件 | 没有 FAT 分区；U-Boot 走 UBI/UBIFS，三族 ubi 命令是既定契约 |
| rootfs 分区格 ext4 | 9.1 裁决过，NAND 上 rootfs 住 UBIFS 卷 |

"三条全对不上。"阿凯自己下结论，"WIC 的分区模型是给 SD 卡、eMMC 画的——tiger 是裸 NAND 加 UBI，没有块设备分区表给它画。出局。IMAGE_BOOT_FILES 跟着出局——它是 WIC 启动分区的供货单，启动分区不存在，**皮之不存，毛将焉附**。"

"那 kernel 和 dtb 的供货谁管？"达哥追问。

"kernel.bbclass 的 do_install。"阿凯答得干脆，"chapter 8 读过，它把 Image 和 dtb 装进打包暂存区 `${D}/boot`，再经 kernel-image / kernel-devicetree 两个包进 rootfs 的 `/boot/`——昨天下午在 NAND 卷里亲眼见过这两个文件。供货不走 WIC 通道，走 rootfs 本身。"

#### 10.1.3 裁决：自写多卷 ubinize 配置加总装脚本

路线落定，两件交付物：**自写多卷 ubinize 配置**（9.5.2 的 ⚠️ 框预告的那条路，今天兑现）和**主机侧总装脚本 `mknandimg.sh`**。配置不单独落盘，由脚本现生成——10.2.3 细说。类里的 `multiubi` / `MULTIUBI_BUILD` 机制 9.5.2 已点名即弃——它为"同一份 rootfs 进多块板"设计，不是"同一板上多个卷"，本章不翻案。

### 10.2 NAND 全量布局：偏移总表与总装脚本

#### 10.2.1 偏移总表：bootloader 段内部也要画格

9.4.3 的三段表把 512 MiB 切成 bootloader / env / nand0，今天细到段内部。拍板值（以 tf-a-tiger / qemu-tiger 仓库实际为准，与 C-W17~C-W21 同批待回填）：

```text
NAND 512 MiB（4096 PEB × 128 KiB，偏移均为 0x20000 整倍数）
bootloader 段  0x0000000 ~ 0x0400000（4 MiB，32 PEB）
  BL1   0x000000 ~ 0x040000（256 KiB，2 PEB）
  BL2   0x040000 ~ 0x080000（256 KiB，2 PEB）
  保留  0x080000 ~ 0x100000（512 KiB，4 PEB，余量）
  FIP   0x100000 ~ 0x400000（3 MiB，24 PEB，含余量）
env 段  0x0400000 ~ 0x0500000（1 MiB，8 PEB）——保持 0xFF 出厂擦除态
nand0   0x0500000 ~ 0x20000000（507 MiB，4056 PEB）
  UBI 三卷：rootfs_a / rootfs_b / data
```

每个偏移拿 0x20000 过了一遍——9.8 坑 2 的算术纪律，今天第一次作为日常动作使用。BL2 和 FIP 之间的保留段也写进表里：画了格的地方，不留没名字的空洞。

#### 10.2.2 自写多卷配置：vol_size 与 autoresize 的分工

动笔前达哥只给了一个提问："每个卷的 `vol_size` 谁定？"

阿凯顺着想：自动生成版靠 `vol_flags=autoresize` 让单卷吃满——**autoresize 一个 UBI 设备上只能有一个卷带**，三卷不能都靠它。答案：rootfs_a/b 显式拍大小，autoresize 只留给 data 卷吃剩余。

算术按纪律先列式子。rootfs 卷拍 64 MiB（core-image-minimal 的 .ubifs 体积以构建实测为准——/boot/Image 一本就可能是 30 MiB 量级，vol_size 余量够不够一并列入回填核对）：`64 MiB ÷ 126976 B = 67108864 ÷ 126976 ≈ 528.5`，ubinize 按 LEB 粒度向上取整——**每卷 529 LEB**（约 64.1 MiB）；两卷 1058 LEB，约 128 MiB。data 卷 attach 时吃掉剩余：按 9.3.2 的 3974 可用块，`3974 − 1058 = 2916 LEB`，约 353 MiB。

rootfs_b 铺同一份 .ubifs 作"出厂镜像"——出厂两套一致，OTA 第一次升级也有完整旧套可回滚；代价是镜像大一份，拍板接受。

配置长这样（三个卷的字段逐一对齐 boot.cmd 契约；data 是空卷，按 ubinize 手册的标准写法**省略 `image=` 行**）：

```ini
# mknandimg.sh 内现生成的 ubinize 配置（10.2.3 的 heredoc，$DEPLOY 生成时展开）
[rootfs_a]
mode=ubi
image=$DEPLOY/core-image-minimal-tiger-aarch64.rootfs.ubifs
vol_id=0
vol_type=dynamic
vol_name=rootfs_a
vol_size=64MiB

[rootfs_b]
mode=ubi
image=$DEPLOY/core-image-minimal-tiger-aarch64.rootfs.ubifs
vol_id=1
vol_type=dynamic
vol_name=rootfs_b
vol_size=64MiB

[data]
mode=ubi
vol_id=2
vol_type=dynamic
vol_name=data
vol_flags=autoresize
```

#### 10.2.3 mknandimg.sh 与整镜构建

总装脚本——本章核心交付物之二。ubinize 配置由脚本里的 heredoc 现生成，`$DEPLOY` 在生成那一刻展开，配置文件与脚本之间不存在"对不上"的缝：

```bash
#!/bin/bash
# 文件路径：~/workspace/meta-tiger/scripts/mknandimg.sh
# NAND 全量总装：bootloader 三件 + nand0 全布局 UBI；env 段保持 0xFF
# 用法：先 source oe-init-build-env，再 bash mknandimg.sh
set -euo pipefail
BUILDDIR=${BUILDDIR:?please source oe-init-build-env first}
DEPLOY=${1:-$BUILDDIR/tmp/deploy/images/tiger-aarch64}
OUT=${2:-tiger-nand-full.img}
UBINIZE=${UBINIZE:-ubinize}	# 主机侧 ubinize，mtd-utils 2.1.6（来源见正文）

# 1. 空白镜像：512 MiB 全 0xFF（NAND 擦除态，9.7.2 的手法）
dd if=/dev/zero bs=1M count=512 | tr '\000' '\377' > "$OUT"

# 2. bootloader 段三件各就各位（偏移见 10.2.1 总表）
dd if="$DEPLOY/bl1.bin" of="$OUT" bs=64K conv=notrunc
dd if="$DEPLOY/bl2.bin" of="$OUT" bs=64K seek=4 conv=notrunc
dd if="$DEPLOY/fip.bin" of="$OUT" bs=1M seek=1 conv=notrunc

# 3. nand0：ubinize 配置现生成；data 空卷省略 image= 行
CFG=$(mktemp --suffix=.cfg)
cat > "$CFG" <<EOF
[rootfs_a]
mode=ubi
image=$DEPLOY/core-image-minimal-tiger-aarch64.rootfs.ubifs
vol_id=0
vol_type=dynamic
vol_name=rootfs_a
vol_size=64MiB

[rootfs_b]
mode=ubi
image=$DEPLOY/core-image-minimal-tiger-aarch64.rootfs.ubifs
vol_id=1
vol_type=dynamic
vol_name=rootfs_b
vol_size=64MiB

[data]
mode=ubi
vol_id=2
vol_type=dynamic
vol_name=data
vol_flags=autoresize
EOF
"$UBINIZE" -o /tmp/tiger-nand0.ubi -m 2048 -p 131072 -s 2048 -O 2048 "$CFG"
dd if=/tmp/tiger-nand0.ubi of="$OUT" bs=1M seek=5 conv=notrunc

# 4. 自检：最终大小必须恰好 512 MiB
[ "$(stat -c%s "$OUT")" = "536870912" ] || { echo "SIZE MISMATCH"; exit 1; }
```

脚本里的 `ubinize` 用 chapter 9 那套 mtd-utils-native 的 sysroot 副本即可——9.8.1 交代过，它不链 lzo，裸跑不用 `LD_LIBRARY_PATH`；想装系统级的也行，`sudo apt install mtd-utils`，版本以 2.1.6 为准。

先交代一句时间线：这份脚本连同最后的自检段，是**踩过坑之后**的样子——第一稿出了什么事，10.7.2 对账。

<!-- 【待验证·阻塞级】C-W17~C-W21 同批口径：bootloader 段内三件偏移为项目拍板值，以仓库实测回填；rootfs 卷 vol_size=64MiB 对含 /boot/Image 的 .ubifs 的余量，随 Image 实测体积一并核对回填 -->

整镜构建——chapter 8 干跑全绿以来的第一次真构建全绿：

```bash

cd ~/workspace/poky
source oe-init-build-env ../build
```

deploy 的 tiger 三件套就位（形态同 9.5.1 对照组，卷名落在 `rootfs_a`）；总装产物 `tiger-nand-full.img`，536870912 字节，自检通过。

### 10.3 切换到完整启动链

#### 10.3.1 还账：defconfig 核查、bootcmd 接线、boot.scr 进卷

chapter 9 的 9.4.2 挂的账，今天第一件事就还：boot.cmd 的三族命令只是纸面契约，前提是 defconfig 里 UBI/UBIFS 符号在编。核查：

```bash
# 核查 u-boot-tiger defconfig 的 UBI/UBIFS/MTD 符号族
grep -E "CONFIG_CMD_UBI|CONFIG_CMD_UBIFS|CONFIG_MTD|CONFIG_CMD_MTDPARTS" \
    ~/workspace/u-boot-tiger/configs/tiger_aarch64_defconfig
```

输出（示意形态，以仓库实测为准）：

```text
CONFIG_MTD=y
CONFIG_MTD_PARTITIONS=y
CONFIG_CMD_MTDPARTS=y
CONFIG_CMD_UBI=y
# CONFIG_CMD_UBIFS is not set
```

注意最后一行的写法——不是"没写"，是"**显式关了**"。这个符号的 Kconfig 带着 `default y if CMD_UBI`：defconfig 里缺行反而默认在编，能被 grep 出一行 `is not set`，说明有人显式禁了它。chapter 7 立 defconfig 时参考的配置里带着这行禁用，当时 boot.cmd 还是纸面契约，没人觉得疼。没有它，`ubifsmount`/`ubifsload` 根本不存在。

顺带翻出第二笔欠账：`CONFIG_EXTRA_ENV_SETTINGS` 里的 bootcmd 还是 chapter 7 的占位骨架 `run distro_bootcmd`——7.6.3 定下的分工（bootcmd 里写"去找 boot.scr 并执行"）从没接过线。今天一并换上真序列。

第三件事：boot.scr 此刻只在 deploy 目录——**它得进卷，bootcmd 才读得到**。翻 u-boot.inc 的 do_install：`UBOOT_ENV` 非空时，它把 boot.scr 装进 u-boot 包的 `/boot/`（实体 `boot-tiger-aarch64-<版本>.scr` + 软链 `boot.scr`），`FILES:${PN}`——这个包带哪些文件的清单——覆盖 `/boot`。也就是说 boot.scr 进 rootfs 后和 Image、tiger.dtb 住同一个目录——bootcmd 读它的路径就是 `/boot/boot.scr`。同一个包还会把 u-boot.bin 搭车带进 `/boot/`，无害，看见别困惑。

给 u-boot 包上板的入口是 `IMAGE_INSTALL`。这行落在哪有个讲究：它是开机链必需的板级陈述，不是宿主机本地项——写进 local.conf 的话，按 chapter10 tag 检出的读者复现不出来（local.conf 不进仓库，chapter 5 起的老规矩）。落 machine conf，和 PREFERRED_VERSION 一个待遇：

```bitbake
# 文件路径：~/workspace/meta-tiger/conf/machine/tiger-aarch64.conf（追加）
# boot.scr 随 u-boot 包进 rootfs 的 /boot/——bootcmd 从卷里读得到它（10.3.1）
IMAGE_INSTALL:append = " u-boot"
```

bootcmd 读 boot.scr 还有一个先后环要解开：A/B 卷选择逻辑写在 boot.scr 里，而 boot.scr 自己住在卷里——bootcmd 从哪个卷读它？答案：固定从 rootfs_a 读。两个卷里的 boot.scr 是同一份 .ubifs 铺出来的，内容一致；A/B 选择等 boot.scr 到手后由它内部的 bootpart 逻辑做。两笔 defconfig 欠账一次还清（diff 形态，示意）：

```text
# 文件路径：~/workspace/u-boot-tiger/configs/tiger_aarch64_defconfig（本章接线 diff，示意形态）
-# CONFIG_CMD_UBIFS is not set
+CONFIG_CMD_UBIFS=y	# 显式写明一眼可见；删掉禁用行也行，default y if CMD_UBI 兜底
-CONFIG_EXTRA_ENV_SETTINGS="bootcmd=run distro_bootcmd\0"
+CONFIG_EXTRA_ENV_SETTINGS="bootcmd=ubi part nand0 && ubifsmount rootfs_a && ubifsload ${loadaddr} /boot/boot.scr && source ${loadaddr}\0"
```

<!-- 【待验证·阻塞级】bootcmd 固定从 rootfs_a 卷 ubifsload /boot/boot.scr 的形态，回填时与 u-boot-tiger 实测一并定死 -->

boot.cmd 这边今早也添了一笔——chapter 7 的雏形全文没有 `setenv bootargs`，9.6.4 认过脸熟的那组内核命令行参数，今天第一次上场。console、ubi.mtd、root 都在这一行里；`root=` 从 9.6.4 预告的字面 `rootfs_a` 换成 `${bootvol}`——跟 boot.scr 里的 A/B 选择走，不再钉死字面卷名：

```text
# 文件路径：~/workspace/meta-tiger/recipes-bsp/u-boot/u-boot/boot.cmd（今晨追加一行）
setenv bootargs console=ttyS0,115200 ubi.mtd=nand0 root=ubi0:${bootvol} rootfstype=ubifs
```

回仓库提交、bump bbappend 的 SRCREV（仓库动一次 SRCREV 跟一次，chapter 7 坑 1 的纪律，一句带过）。boot.cmd 是 meta-tiger 的 `file://` 附件，不进 u-boot-tiger，没有 SRCREV 可 bump——它的改动靠重建自动进 boot.scr。随后动作链别漏：重建 u-boot（boot.scr 随 mkimage 管道顺带重打）→ 重建 core-image-minimal（`IMAGE_INSTALL` 生效，boot.scr 进 .ubifs）→ 重跑总装脚本。此刻 FIP 里还没有 BL33——下一节就拧；把总装写成脚本，为的正是产物一变就重跑。

重建后老手法实物确认——`-bios u-boot.bin` 单跑进命令行：`=> help ubi` 在列；UBIFS 一族在 v2024.04 里是四个独立命令，没有 `ubifs` 父命令，`=> help` 全列表里逐个指认 `ubifsmount` / `ubifsload` / `ubifsls` / `ubifsumount`；再 `=> printenv bootcmd`，新序列在。账还清了。

#### 10.3.2 TFA_UBOOT=1：BL33 进 FIP

第二个动作：拧上 chapter 7 的 7.1.2 混过脸熟的预埋旋钮。**TFA_UBOOT** 就地解释：meta-arm TF-A 配方变量，BL33 进 FIP 的开关——设 `"1"`，配方自动依赖 u-boot、等它的 do_deploy，再把 `u-boot.bin` 作为 BL33 递给 TF-A 的 Makefile。bbappend 末尾追加一行：

```bitbake
# 文件路径：~/workspace/meta-tiger/recipes-bsp/trusted-firmware-a/trusted-firmware-a_%.bbappend（追加）
# chapter 10：拧上 meta-arm 预埋旋钮（7.1.2），BL33=u-boot.bin 进 FIP，
# 条件 DEPENDS 随之把 u-boot 拉上 TF-A 的构建依赖链
TFA_UBOOT = "1"
```

重建并验证：

```bash
# 重建 TF-A（u-boot 被条件依赖拉起，先等它的 do_deploy）
cd ~/workspace/poky
source oe-init-build-env ../build
bitbake trusted-firmware-a
# 看 EXTRA_OEMAKE 终值里 BL33= 的落点
bitbake -e trusted-firmware-a | grep ^EXTRA_OEMAKE=
# 对比 FIP 体积（BL33 进包前后）
ls -l tmp/deploy/images/tiger-aarch64/fip.bin
```

输出（关键行，示意形态）：

```text
EXTRA_OEMAKE=" ... PLAT=tiger ... BL33=<deploy 目录>/u-boot.bin"
-rw-r--r-- ... 1.6M ... fip.bin		# 进包前约 0.9M，明显见涨
```

FIP 里第一次有了 BL33。产物变了，总装脚本重跑一遍——这正是把总装写成脚本的理由。

记住这个旋钮的连带代价，下午就要用到：BL33 是在 TF-A 构建期固化进 FIP 的，从此 **u-boot 动一次，FIP 就得跟一次**——只重建 u-boot，deploy 里的 fip.bin 装的还是旧 BL33。

#### 10.3.3 起跑方式切换：-bios bl1.bin 与 runqemu 接线

前几章都是单级直通：`-bios bl1.bin` 只跑 TF-A、`-bios u-boot.bin` 只跑 U-Boot、`-kernel Image` 直递内核。今天起跑点挪到链的最顶端——`-bios bl1.bin` 加全量 NAND 镜像，BL1→BL2→BL31→U-Boot→kernel 一条龙。

runqemu 侧有个先决问题：machine conf 第四段（chapter 5 落地）写着 `QB_DEFAULT_KERNEL = "Image"` 和 `QB_KERNEL_CMDLINE_APPEND = "console=ttyAMA0"`——runqemu 默认会拼出 `-kernel Image -append ...` 的直通装载，和 `-bios bl1.bin` 的全链路径**抢同一个起跑点**。要切全链，先把默认直通摁掉。machine conf 末尾追加一段（QB_* 一族的机制 chapter 4 的 4.6 讲透过，chapter 5 落地进本机 conf）：

```bitbake
# 文件路径：~/workspace/meta-tiger/conf/machine/tiger-aarch64.conf（末尾追加）
# ---- 全链启动接线（chapter 10）----
# 起跑点从直通装载挪到链顶 BL1：摁掉 runqemu 的默认 -kernel 直通
# 注意：下面两行是对第四段同名赋值的覆盖——BitBake 后赋值生效，并存两处不冲突
QB_DEFAULT_KERNEL = "none"
# console 不再由这里递——全链里轮到 boot.scr 的 bootargs（下午就知道为什么）
QB_KERNEL_CMDLINE_APPEND = ""
# QB 原生参数够不着 -bios 与 NAND 后端；QB_OPT_APPEND 是追加口子——
# runqemu 拼 QEMU 命令行时把它的值原样接到末尾
QB_OPT_APPEND = "-bios ${DEPLOY_DIR_IMAGE}/bl1.bin <NAND 镜像接法参数，以 qemu-tiger 后端为准>"
```

```bash
qemu-system-aarch64 -machine tiger -cpu cortex-a53 -smp 4 -m 1024 \
```

### 10.6 调试方法论：哪一段挂的

#### 10.6.1 六级分段与各段串口指纹

阿凯把日志从头翻到尾，一个发现冒出来：这条链上每一级，打印的东西**长相都不一样**。他把六级各自的"串口指纹"列成表：

| 段 | 串口指纹（这段活着的证据） |
|----|--------------------------|
| BL1 | `NOTICE:  BL1: v2.10.4...` |
| BL2 | `NOTICE:  BL2: ...`（含 DDR 初始化行） |
| BL31 | `NOTICE:  BL31: ...` + `INFO: BL31: Preparing for EL3 exit...` |
| U-Boot | banner `U-Boot 2024.04...` + `Hit any key to stop autoboot` |
| Kernel | `Starting kernel ...`（U-Boot 打印）→ `Booting Linux...` / `Linux version 6.6...` |
| rootfs | `Run /sbin/init as init process` → `tiger-aarch64 login:` |

表里几行值得掰开说。BL31 的指纹为什么多带一行 `INFO: Preparing for EL3 exit`？前面那行 `NOTICE:` 只证明 BL31 活着，这行 INFO 是**移交发生**的证据——看到它，说明 BL31 不但活着，还把权交出去了，问题就不会出在"BL31 没移交"上。

Kernel 段的指纹为什么拿 U-Boot 打印的 `Starting kernel ...` 开头？因为交接动作恰好跨两段：这行字是 U-Boot 说的，内容是"我要把控制权给内核了"。它出现，说明交接动作完成了，锅过了这道门槛；随后 `Linux version 6.6...` 才是内核自己开口的第一句。

rootfs 段的 `Run /sbin/init` 同理——那是内核挂上了根、拉起用户空间的证据，归 rootfs 交接面**之后**；`login:` 提示符是终点。判断口诀就此落定：**看串口最后一行归哪段——停在哪段，问题就在哪段，或它与上一段的交接面上**。

套到眼前的日志：BL1/BL2/BL31 的指纹都在，banner 也在——四级全活着；`Starting kernel` 不在，问题圈定在 BL33 段内部。

#### 10.6.2 交接面清单

段内没问题时看交接面。全链三处交接面，是本章调试的主索引：

1. **BL31→BL33**：FIP 里有没有 BL33（10.3.2 刚验证过，排除）。
2. **U-Boot→Kernel**：dtb 地址、bootargs——booti 的三个参数和内核命令行。booti 是 chapter 7 boot.cmd 雏形里认过脸熟的 Image 启动命令，今天第一次真跑。
3. **Kernel→rootfs**：`ubi.mtd=` / `root=` / 卷名——内核命令行与 UBI 布局的对表。

另外记住一条区分：**没有输出 ≠ 死机**。内核的 console 没指对时会"假死"——可能还在跑，也可能已经 panic，串口上一个字都看不见。这和真挂的区分不靠等，靠推理——待会儿就用得上。

#### 10.6.3 锁定坑 1：U-Boot 段的环境变量出厂值

指纹定在 BL33 段，阿凯对着日志逐行读：唯一的报错行是 `Partition nand0 not found!`——nand0 这个名字 U-Boot 不认识。bootcmd 的 `ubi part nand0` 挂在这一步，后面的 `&&` 链自然断掉，boot.scr 连被读的机会都没有。

nand0 的名字解析靠什么？就地解释一句：**mtdids / mtdparts**，U-Boot 侧的两个环境变量，MTD 设备名与分区命名的对表，`mtdparts` 里 `-(nand0)` 的 `-` 表示"到设备末尾"。进命令行查证，顺带把 boot.cmd 和 bootcmd 里点名的变量全列出来挨个问一遍：

```text
=> printenv mtdids mtdparts
## Error: "mtdids" not defined
## Error: "mtdparts" not defined
=> printenv kernel_addr_r fdt_addr_r loadaddr
## Error: "kernel_addr_r" not defined
## Error: "fdt_addr_r" not defined
## Error: "loadaddr" not defined
```

五连空。nand0 对不上只是第一个咬人的——`kernel_addr_r` / `fdt_addr_r` / `loadaddr` 同样从没定义过，今天不补，下一次起跑还得回来。**犯错位**在 u-boot-tiger 的 defconfig：chapter 7 时代写的 `CONFIG_EXTRA_ENV_SETTINGS` 只给了 bootcmd 骨架，地址变量和命名对表从没写过。boot.cmd 的每一行纸面契约，今天第一次咬人。

顺带划一条边界：9.6.2 否决过内核侧的 mtdparts——彼处否决的是"同一事实在 dts 和命令行写两遍"；此处是 U-Boot 与内核**两个组件各自需要分区知识**，属组件边界的必要双写，不翻案。

修正（diff 形态，示意）：

```text
# 文件路径：~/workspace/u-boot-tiger/configs/tiger_aarch64_defconfig（坑 1 修正 diff）
 CONFIG_DEFAULT_DEVICE_TREE="tiger"
-CONFIG_EXTRA_ENV_SETTINGS="bootcmd=<读 boot.scr 序列，10.3.1 已落位>\0"
+CONFIG_EXTRA_ENV_SETTINGS="mtdids=nand0=<控制器设备名>\0\
+mtdparts=<控制器设备名>:4M(bootloader),1M(env),-(nand0)\0\
+kernel_addr_r=0x42000000\0fdt_addr_r=0x46000000\0loadaddr=0x41000000\0\
+bootcmd=<读 boot.scr 序列，10.3.1 已落位>\0"
```

panic 行——和 chapter 8 那次**同一行字**。但含义全变了：那次 `"(null)"` 是"地没有"；这次点了名的 `ubi0:rootfs_a` 是"**地契对不上**"。分段定位：指纹进了内核、死在 rootfs 交接面（10.6.2 第 3 处）。对账三处数字：

- 内核日志自报：`nand: 64 MiB`——QEMU 后端眼里的芯片只有 64 MiB；
- 主机侧：`ls -l tiger-nand-full.img` → **67108864 字节**；
- dts 与总表：nand0 声明到 `0x20000000`——512 MiB 布局。

64 对 512。链条逐级拆开：QEMU 按后端的选片规则把这片 NAND 当成了 64 MiB 的芯片（选片规则是 qemu-tiger 的实现细节，随 C-W19 同批回填）；内核按真实芯片对 dts 分区表，nand0 开头 5 MiB 在界内、末尾越界——于是有了那行 `extends beyond the end of device ... -- size truncated`，分区没被禁掉，是被**截断**到 59 MiB。

截断后的 nand0 剩 59 MiB，472 块，扣掉 UBI 自留的卷表（2 块）和坏块预留（约 9 块），凑出 460 块上下的好块。而卷表上 rootfs_a 一个卷就声明了 **529 个 LEB**——上午 10.2.2 刚算过的那笔账，在这里回响：UBI attach 前的卷表核查发现声明的胃口喂不饱，当场拒收，`ubi0` 不存在，root 自然打不开。

那 64 MiB 是哪来的？阿凯翻开 mknandimg.sh——第一稿空白镜像那行是 `count=64`：他调脚本时图快，先拼个小镜像把管线试通（64 MiB 够装 5 MiB 的 bootloader 加二十来 MiB 的 UBI 载荷），试通后忘了放大到 512，大小自检也是坑后补的。第一稿实物：

```text

-dd if=/dev/zero bs=1M count=64 | tr '\000' '\377' > "$OUT"	# 第一稿：先拼个小的试管线，忘了放大
+dd if=/dev/zero bs=1M count=512 | tr '\000' '\377' > "$OUT"
+[ "$(stat -c%s "$OUT")" = "536870912" ] || { echo "SIZE MISMATCH"; exit 1; }
```

**犯错位在今晨的总装脚本，发作段在 kernel→rootfs 交接面**——离拼装动作十万八千里，chapter 9 的踩坑族谱又添一笔。还有个事后才看清的细节：上一次起跑它其实就 panic 了——console 指错，没人听见。修正：`count=512`、补上自检段、重拼镜像、复验 536870912 字节。这就是 10.2.3 那份脚本带自检段的由来。

"所以这局双赢。"达哥把笔递给阿凯，"咖啡一人一杯。"

阿凯接过笔，把启动链图旁边添的最后一行字写完：**从 BL1 到 login，全链通电。**然后他想起早上那三个字的步骤："跑、看、修——我修了三次才算入门。"

"三次都是教科书级的位置。"达哥说，"U-Boot 段一次、kernel 段一次、rootfs 交接面一次——从上游到下游各响一个雷。下一回再响，你自己就知道先对哪张表了。"

### 10.8 踩坑实录收束：分段定位表落纸

三个坑的"犯错位 vs 发作段"对照，落纸存档：

| 坑 | 犯错位 | 发作段 | 症状指纹 |
|----|--------|--------|---------|
| 1. env 出厂值缺失 | u-boot-tiger defconfig（chapter 7 时代欠账） | U-Boot 段 | banner 在、`Partition nand0 not found!`、`Starting kernel` 不在 |
| 2. console 指错（ttyS0） | boot.cmd 的 bootargs 行（今晨，9.6.4 参数组第一次上场） | Kernel 段起点 | `Starting kernel ...` 后再无一字（假死） |
| 3. 镜像大小手滑 | mknandimg.sh 第一稿（今晨） | Kernel→rootfs 交接面 | nand0 截断 + UBI attach 拒收 + panic 行 |

和既有踩坑族谱的关系：chapter 5~8 是"什么都不发生"系列（BitBake 视野之外不替你知道），chapter 9 是"参数放行型"（工具视野之内照样放行），本章新增**"契约错配型"**——单级验证时契约根本不在场，串联那一刻才开始咬人。防法就是 10.6 那张六级分段表：最后一行归哪段，问题就在哪段。

> **⚠️ 注意**：卷名一致性——`rootfs_a` / `rootfs_b` 这组名字在 machine conf（UBI_VOLNAME）、ubinize 配置（vol_name）、boot.cmd（${bootvol}）、内核命令行（root=ubi0:）多处会师过，任何一处敲错都是坑 3 同族的发作形态。改名时全局检索，不凭记忆。

> **⚠️ 注意**：autoresize 再钉一次——多卷布局里它只能属于 data 卷。给 rootfs 卷也带上，A/B 两卷就没有立足之地（9.5.2 预告、本章 10.2.2 兑现）。

### 10.9 本章小结

白板七步回顾：

- **10.1**：WIC 与 IMAGE_BOOT_FILES 首次正式引入即裁决出局——块设备分区模型 vs 裸 NAND + UBI；kernel/dtb 供货走 kernel.bbclass do_install 的 `${D}/boot`、经包进 rootfs 的 `/boot/`；路线定为自写多卷 ubinize 配置 + 总装脚本。
- **10.2**：偏移总表细到 bootloader 段内部（BL1/BL2/FIP 各自偏移加保留格，全按 0x20000 过检）；三卷分工（rootfs_a/b 各 64 MiB 显式 vol_size——529 LEB 的算式落纸、data 空卷省略 `image=` 行并独占 autoresize，rootfs_b 铺同一份出厂镜像）；`mknandimg.sh` 总装（空白镜像 0xFF、dd 三件、heredoc 现生成配置跑 ubinize、铺 seek=5、大小自检）；tiger 整镜第一次真构建全绿。
- **10.3**：还 chapter 9 的账——defconfig 核查揪出显式禁用的 `CONFIG_CMD_UBIFS`（半坑，走 SRCREV 纪律补齐）；bootcmd 从 chapter 7 的占位骨架接线上真序列（固定从 rootfs_a 读 `/boot/boot.scr`，先后环解开）；boot.scr 经 u-boot 包的 `/boot/` 进卷，`IMAGE_INSTALL:append = " u-boot"` 落 machine conf 不落 local.conf；boot.cmd 补上 bootargs 行（9.6.4 参数组第一次上场，`root=` 随 A/B 换成 `${bootvol}`）；`TFA_UBOOT = "1"` 拧上，BL33 进 FIP（EXTRA_OEMAKE 的 BL33= 落点 + fip 体积双验证，连带代价"u-boot 动一次 FIP 跟一次"点明）；起跑切到 `-bios bl1.bin` 全链，runqemu 侧摁掉默认直通、用 QB_OPT_APPEND 接线。
- **10.4**：PSCI 伏笔回收条件齐（BL31 第一次全链在场 + dts 的 psci 节点）；SMP 首次正式引入，验证落点押后到成功后。
- **10.5~10.7**：三轮失败，症状从上游向下游各推进一段——U-Boot env 缺出厂值（分段定位法首秀）→ console 指错假死（"没有输出 ≠ 死机"，stdout-path 反推出口）→ NAND 大小对账 panic（nand0 截断、卷表 529 LEB 喂不饱、attach 拒收；与 chapter 8 同一行字，含义从"地没有"变成"地契对不上"）；第四次起跑 BL1→login 全通，`smp: Brought up 1 node, 4 CPUs` + `nproc`=4 实证 SMP；赌约按字面达哥认输、按过程赢回半局，双赢收场。
- **10.8**：分段定位表落纸——六级指纹 + 三处交接面；踩坑族谱新增"契约错配型"。

本章产出清单：

- `meta-tiger`：新增 `scripts/mknandimg.sh`（ubinize 配置内嵌 heredoc 现生成）；`trusted-firmware-a_%.bbappend` 追加 `TFA_UBOOT = "1"`；boot.cmd 追加 bootargs 行并在坑 2 修正（console=ttyAMA0）；machine conf 追加 `IMAGE_INSTALL:append = " u-boot"` 与全链启动接线段（QB_DEFAULT_KERNEL / QB_KERNEL_CMDLINE_APPEND / QB_OPT_APPEND）。
