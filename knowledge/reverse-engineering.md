# Linux 与 Windows 可执行文件逆向分析

用于理解已授权目标的程序结构、关键逻辑与可观察行为，为研发分析和调试提供可复核的证据。具体样本、问题、目标系统和允许的操作由实际任务确定；知识配置本身不代表已经取得样本、执行许可或工具环境。

## 输入与样本识别

先明确要回答的问题与分析边界，记录样本来源、文件路径、版本、大小和 SHA-256，保留原始样本，以副本开展分析。关联库、配置、测试输入与调试资料也应记录版本，避免把不同构建的证据混用。缺少样本或目标时说明缺口，不预造分析结论。

根据文件内容识别格式、目标架构、位数、字节序和运行时，再选择分析方式，不凭扩展名或当前主机判断目标。遇到托管代码、不同指令集或特殊格式时按实际目标调整方法，不一律套用本机原生汇编分析。

## 文件结构与地址

- 对 ELF，结合文件头确认类型、架构和入口，区分节表与用于装载的程序头；根据可装载段核对磁盘内容与内存映像，不把两者的偏移或大小直接等同。结构依据见 [ELF Header](https://gabi.xinuos.com/elf/02-eheader.html) 与 [Program Loading](https://gabi.xinuos.com/elf/07-pheader.html)，系统和架构细节另查目标适用的 ABI。
- 对 PE，核对机器类型、入口、节和相关数据目录，按问题追踪导入、导出、重定位及调试信息。明确区分文件偏移、RVA 和 VA，不能把 RVA 直接当作文件偏移。结构依据见 [Microsoft PE Format](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format)。

引用位置时注明样本、模块、地址类型及映射依据；涉及运行时地址时记录实际装载位置。只对确有文件内容映射的区域换算磁盘位置，不把仅存在于内存的区域硬套为文件偏移。

## 静态分析

围绕目标问题，从入口、字符串、符号、库依赖及交叉引用定位相关代码，再梳理调用关系、控制流、数据流、关键数据结构、输入输出和异常路径。对重要判断回看原始字节或反汇编，不把工具自动命名、推测类型或反编译伪代码视为恢复出的原始源码。

区分直接证据与假设。函数名、字符串或导入项只能作为线索，不能单独证明某段逻辑实际执行；符号缺失、优化、混淆或打包导致无法确认时，记录限制和待验证问题，不臆补未知逻辑。

## 动态验证

先以静态结果提出可验证假设，仅在任务授权和隔离条件满足时运行或调试样本。确认目标系统、依赖、输入和可恢复的实验环境；未知样本不直接在日常主机或生产环境执行，不自动连接真实业务网络或使用真实凭据。需要额外权限或外部服务时先说明需求。

按目标选择可用的调试和行为观测工具，记录实际版本、参数、断点位置、输入、日志及观察结果。工具是否可用要实际核对，不将成员配置视为已安装工具。对关键结论结合静态逻辑和重复实验验证；单次未观察到某行为不等于程序不存在该行为。

未具备动态条件时，可交付静态分析及待验证清单，但明确哪些结论尚未经过运行验证。需要编写辅助脚本时保持用途局限于获授权分析，提供输入说明、使用方法及与风险相称的检查，不覆盖原始样本。

## 分析交付

报告围绕任务问题组织，包含样本标识、环境与方法、覆盖范围、关键逻辑说明、必要的伪代码或调用关系、证据位置、复现步骤、结论及未解决问题。明确标记“已观察事实”“分析推断”“待验证”，说明置信依据与适用版本；不能用推测补成确定结论。

交接时提供可继续定位的地址和可访问的证据，避免只留截图或无法重现的口头描述。未经授权不上传样本、内存转储或敏感日志到外部分析服务；发布或共享前核对资料范围与敏感信息。
