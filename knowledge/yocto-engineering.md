# Yocto 工程

本知识用于基于 Yocto Project、OpenEmbedded 与 BitBake 开发和维护嵌入式 Linux 系统。它提供工程方法和判断依据，不自行授予硬件访问、凭据使用、外部仓库写入、签名或发布权限。

## 固定可复现基线

开始修改前记录宿主系统、Yocto 发布系列、Poky 与各 layer 的仓库地址和提交、BitBake 版本、`MACHINE`、`DISTRO`、镜像目标及关键构建配置。分支名和浮动标签不能代替提交基线；配置片段、环境变量、镜像和 SDK 都应能追溯到同一组源码与元数据。

将自有 metadata 与上游 Poky、BSP layer 分开维护。使用 `bitbake-layers show-layers`、`show-recipes`、`show-appends` 等命令核对 layer 注册、优先级、配方选择和追加文件实际生效情况。`LAYERSERIES_COMPAT`、layer 依赖、许可证和版本约束须与目标发布系列相符。

## Metadata 开发

按 layer 的 `BBFILES` 规则组织 recipe、append、class、include 和配置文件，不把目录惯例误写成 BitBake 的普遍强制规则。配方应明确源码来源与锁定信息、许可证及校验、构建依赖、运行依赖、任务行为、安装内容和打包边界。

优先通过自有 layer、`.bbappend`、补丁或可复用 class 集成改动，避免直接修改上游 layer 和 `tmp/work` 中的临时文件。使用 `devtool` 开发或升级配方时，区分工作区状态、正式补丁和最终 metadata；完成后检查没有只在本机工作区生效的隐式改动。

变量、override、继承关系和任务依赖以当前版本实际展开结果为准。需要定位时使用 `bitbake -e`、任务日志、运行脚本和依赖图等证据，说明最终值来自何处；不凭片段顺序猜测覆盖结果。

## 系统集成

区分发行版策略、机器与 BSP 能力、镜像内容和应用配方的职责。内核、bootloader、设备树、固件和机器特性变更须对应目标硬件与启动链；镜像、包管理、init 系统、安全和调试选项须区分开发态与交付态。

SDK 与 eSDK 需要验证安装、环境初始化、交叉编译、sysroot、部署和目标运行的完整闭环。生成镜像或 SDK 只证明构建阶段成功，不能代替 QEMU 启动、实机启动、外设验证或应用行为验证。

## 构建与故障定位

先保留失败任务、首个有效错误、`log.do_*`、`run.do_*` 和磁盘/网络状态，再决定是否清理或重跑。根据影响范围选择单任务重跑、配方清理或新构建目录；不把 `cleanall`、删除缓存或反复重试当作默认修复手段。

区分下载缓存、共享状态缓存和构建输出。缓存可以提速，不能替代从已记录基线复现构建的证据。依赖升级、工具链变化、宿主差异或签名变化后，检查缓存是否仍适用，并保留必要的磁盘容量和失败恢复方案。

## 验证与交接

按变更风险选择验证层级：metadata 解析、目标任务构建、镜像构建、QEMU 启动、实机启动、外设与升级流程分别记录，不能用较低层结果替代较高层结论。破坏性实验应先定义备份、恢复和终态检查，避免给共享环境留下未说明的配置或工作树改动。

交付时记录执行日期、环境和源码基线、命令、预期、实际结果、返回码、日志或制品路径、校验值、工作树终态和未覆盖项。失败应说明复现方式、初步定位、受影响范围与下一步，不修改预期来掩盖问题。
