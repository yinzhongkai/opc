## 3. 评审组织

- **平台设计前置**：T-016 由 architect 主责版本化设计，先区分来源事实、候选取舍与待确认问题；候选稿提交明确版本后，由 project-manager 登记两名工程成员的设计专业核对及用户意见。全部意见到齐后 architect 统一修订，必要复核与用户确认形成本章实施基线。设计确认不等于代码实现或实测通过。
- **逐章修订**：writer 修订并自查；reviewer 独立审校（技术准确性），重点见 A-001 §4.4。
- **内部流程清理**：writer 按 D-011 在每章自动检查读者可见的 `task NN` 与为本书设置的章末 Git tag 流程；前者改用 chapter/章/节或自然衔接，后者删除。实际教学需要的上游版本 tag 或发布 tag 按技术语义保留。
- **逐章真实环境核验**：每章登记可验证对象，执行成员及范围以对应任务为准；T-016 由 qemu-engineer 交付模型测试证据，yocto-engineer 交付集成、干净构建与系统验证证据，reviewer 对稳定正文与匹配证据独立技术审校。记录执行者、环境版本、正文版本、命令、预期、实际结果、证据位置与状态；模型测试与系统启动分别记录，开发者自测不替代独立审查。官方资料或源码核查不能冒充实际执行；不适用项逐条说明原因。
- **交叉评审**：试读版节点在任务内安排轻量评审（PROJECT_PROTOCOL 第 4.1 节），由 project-manager 登记安排；**用户通读意见同期提交**（D-007，2026-09-19：用户通读受评章节提出建议/疑问，经 project-manager 汇集登记）；用户意见与全部评审者意见到齐后，writer 一并统一修订。
- **验收收口**：章节定稿以 D-003/D-010/D-011/D-013 为准——评审通过 + 本章逐章真实环境核验完成 + 涉及该章的 C-W/V 项实测消除（D-001）+ 临时 workspace 清理后仍可由 Poky + `meta-tiger` 复现（D-013）+ 内部流程清理完成 + 用户确认。
- **用户通读并行**：用户持 A-003 通读校验随时进行；结论回流路径见 STATUS 通读期协作约定。
