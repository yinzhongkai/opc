## 3. 讨论如何演变

### 产品线

四属性设想 → 在声光之外增加触觉 → 收敛到仅振动输出 → 引入振动语言 → 明确区块链只做存证、不做 NFT → 由概念方案推进到待评审 PRD。

Kimi 增加过人际振动消息、语言扩展包、专属振动签名、限定材质和联名等建议。用户没有逐项确认这些新增功能。用户说“按你的建议来”发生在“补充 MVP 定义、用户故事等 PRD 内容”的建议之后，表示同意继续整理文档，不能把随后新写出的全部功能、指标或发布计划都视为已批准。

### 架构线

初稿包含灯光、音频、Wi-Fi、旋钮和触摸 → 用户要求接口隐藏 → 用户去掉灯光和音频，强调百台互动 → Kimi 将主控建议从 ESP32-S3 改为 nRF52840 → 形成一版综合方案 → 用户要求降成本 → 用户提出立方体翻面选时、摇晃切换 → 继续讨论外壳对蓝牙的影响以及开发板和模块接线。

综合技术方案出现在立方体交互与材质讨论之前；不能把该“V1.0 定稿”标题当作覆盖后续全部要求的最终方案。

## 4. 两份材料中的差异与残留

| 主题 | 材料中的不同表述 | 记录处理 |
|---|---|---|
| 形态与输入 | 产品稿保留球体／多面体、拍击／旋转；架构对话中用户后来提出立方体、翻面与摇晃 | 保留演变；本项目建项方向采用用户提出的立方体交互，细则待定义 |
| 输出 | 用户要求只用振动；架构稿仍保留接口仓隐藏灯 | 隐藏灯不是默认已确认配置 |
| 首版范围 | PRD 将场域同步放到 P2 独立项目；架构稿较早验证同步并安排酒吧试点 | 首阶段范围与验证优先级尚未统一 |
| 区块链 | 架构稿仍讨论数字藏品、铸造和转赠；产品用户明确不做 NFT | 按纯存证方向记录，技术与业务规则待设计 |
| 充电 | 用户提出单充电口与特制盖；产品概念稿另写无线充电底座 | 无线充电属于 Kimi 增加的方案，未确认 |
| 场域通信 | 产品稿偏向私有 2.4GHz 广播；架构稿偏向 BLE 广播与未来时刻执行 | 两者均保留为历史候选，未完成正式选型 |

## 5. 后续需要明确的问题

这些是材料中的缺口清单，不是已指派的成员任务，也未预设截止日期。

1. 首阶段主要验证桌面计时留存、振动体验，还是同时验证百台同步？两条验证线如何与首发范围区分？
2. 六个面各代表什么；翻面开始、暂停、重置、停止如何区分；摇晃与携带、跳舞、马达振动如何区分？
3. 桌面使用时用户怎样感知提醒；机械噪声、振动传导、不同桌面和持握方式的体验如何评价？
4. 振动语言先支持哪些词汇；“质感”是否必要；设备／批次之间怎样保持辨识一致性？
5. 同步要测设备之间的偏差还是与音乐的偏差；在什么人数、距离、遮挡、无线干扰和运行时长下验收？
6. 选哪一主控、协议栈、马达、驱动与加速度计；如何完成无线、时钟、升级和供电的实际验证？
7. 外壳材质、天线位置、密封、耐摔、温升和充电姿态如何共同取舍？
8. 区块链、硬件密钥、编号与振动签名分别证明什么；生产注入、查验和实物流转如何绑定？
9. BOM 与售价目标基于多大数量、哪些成本口径；哪些一次性投入需要单独估算？
10. App、云端、存证、人际消息和场控分别在哪一阶段进入范围；正式验收和协调记录由谁维护？
