## 1. 书稿现状（综合盘点）

本节为项目经理结构盘点与 A-001 评估结论的合并视图；逐章细节与技术风险清单以 [A-001](A-001-书稿现状评估.md) 为准，此处不重复。

### 1.1 基本情况

- 书稿位于仓库根 `yocto/`，共 22 个章节文件、约 91 万字节：前言、序章、正文 chapter 1–16、尾声、附录 A/B/C。
- 全书叙事弧完整闭环（序章立项 → 16 章任务推进 → 尾声回收伏笔），章节骨架高度统一（16 个技术章全部有"本章小结""踩坑实录""延伸阅读"），版本基线全书一致（Scarthgap 5.0 / 内核 6.6 LTS / TF-A 2.10.4 / U-Boot v2024.04 / QEMU 8.2.7），每章末 git tag 书签体系自洽。
- 质量分层明显：chapter 1–5 基于真实 poky 环境验证、零待验证标记；chapter 6–16 与附录 A 含约 85 处待验证注记（其中 48 处阻塞级），构建输出、串口日志、耗时体积数字为"按机制书写的示意形态"。[A-001](A-001-书稿现状评估.md "citation")，§0、§4

### 1.2 主要缺口

| # | 缺口 | 证据 | 影响 |
|---|---|---|---|
| 1 | 前言承诺与草稿现状矛盾 | 前言声明"书中所有代码示例均经过实际构建验证"；正文大量注记标注输出为"示意形态，严禁直接采用，以仓库实测回填为准" | 出版级硬伤：不实测就必须改前言口径 |
| 2 | 四个开发态仓库不存在 | qemu-tiger / tf-a-tiger / u-boot-tiger / linux-tiger 为虚构占位（SRCREV 全零），chapter 6–16 大量内容依赖其就位；单点风险最高处为 NAND 几何拍板值（页 2 KiB / 块 128 KiB / 512 MiB），chapter 9 全部算术依赖它 | 决定技术验证的真实成本，可能超过文字修订本身 |
| 3 | 写作工作流资料未随稿迁移 | "待验证清单"（C-W1–C-W35、V8–V41 编号）、`glossary.md`、`configs/numbering.md`、`outline/`、`state/` 均被正文引用但不在本仓库 | 验证项无法清点跟踪；两处 glossary 出入无法裁决 |
| 4 | `yocto/index.md` 不完整且有悬空引用 | 章节表只列到 task15（chapter 14），缺 task16–task21 共 6 行（经直接读取核实）；task07–11 文件名弯引号与实机下划线不符；三个引用路径不存在 | 目录页不可靠 |
| 5 | 体例与跨章事实出入 | 章节标题层级与编号风格不一；2 处"第 N 章"旧式引用；chapter 8 deploy 路径（ipk vs rpm）出入已自我标注待裁决；前言自身无 `preface` tag | 统稿阶段处理，成本可控 |

### 1.3 关键判断

草稿的"文字完成度"远高于"验证完成度"。打磨工作的最大变量是缺口 1–3 指向的同一个决定：**技术内容是否真实构建验证、验证到什么深度**。它直接改变工作量数量级，必须排在章节计划之前由用户拍板（D-001）。这一判断与 A-001 的建议顺序一致。

## 2. 阶段划分建议

依据图书生产知识"先闭环一章、再验证关联章节与全书"的原则：

| 阶段 | 内容 | 出口条件 |
|---|---|---|
| P0 范围确认 | 用户逐项确认 DECISIONS.md 中 D-001–D-006 | 相关决定全部 confirmed |
| P1 基础修复 | 补全/修正 index.md；统一编号与文件名体例；落实待验证清单与 glossary 的载体（作者提供原文件或按正文注记重建为可跟踪清单）；裁决 2 处跨章事实出入 | 目录页可靠、验证项可跟踪、无悬空引用 |
| P2 章节闭环试点 | 选一章走完整流程（修订 → 交叉评审 → 统一修订 → 复核 → 试读版）。建议 chapter 1"把 Yocto 跑起来"：依赖最少、无 C-W 阻塞项 | 协作流程本身被验证，评审节奏与记录方式定型 |
| P3 全书章节修订 | 按工程依赖序逐章打磨（chapter 1→16，边界章与附录穿插）；含阻塞级注记的章节按 D-001 确认的口径分批处理，验证结论回填前不进"章节定稿" | 各章达到确认的定稿标准 |
| P4 全书统稿与输出 | 跨章一致性（术语首次讲解、依赖回指、示例演进）、遗留项清点、输出前登记（章节及版本、环境基线、批准依据、明确排除内容） | 按确认的交付物形态完成交付登记 |

## 3. 评审组织建议

- **逐章修订**：writer 负责章节修订与作者自查；reviewer 负责独立审校，重点清单见 A-001 §4.4（chapter 15 人为构造的 watchdog bug、chapter 8 CVE patch 时间线预判、chapter 16 license 命中结论等）。
- **交叉评审**：在"试读版"节点安排任务内轻量评审（PROJECT_PROTOCOL 第 4.1 节），评审安排由 project-manager 登记，意见与处理回复留在任务内；本轮全部评审者提交后作者再统一修订。
- **试点先行**：P2 跑通后再铺开 P3，避免 22 章同时进评审造成协调拥塞。
