## 笔记组织方式

| 主要入口 | 适合的阅读方式 | 需要承担的整理工作 | 本项目建议 |
|---|---|---|---|
| 按书组织 | 围绕一本书持续阅读，回看作者论证与自己的理解变化 | 跨书观点需要另建链接或主题页 | 作为主要入口 |
| 按主题组织 | 围绕明确问题同时读多本书、比较不同作者 | 更早需要拆分条目，维护来源和主题分类 | 在材料积累后按需增加 |
| 按日期组织 | 随手捕捉零散阅读感受，保留时间过程 | 回看一本书时需要从多天记录中汇集内容 | 作为临时收集方式 |

每书一目录，先只有一份主笔记。开读前写想解决的问题，阅读中按日期与章节追加记录，读完或暂告一段落时补全回顾。长篇论证、练习或章节记录影响主笔记浏览时，再拆成章节文件，主笔记保留导航与总结。

主题笔记围绕具体问题建立，例如“哪些条件下某个观点成立”。它记录跨书比较和自己的判断，并链接回各书笔记的出处；摘录和阅读记录仍保留在原书笔记中。没有比较需求时可以先不建立主题页。

以下为拟议工作区结构，目录和文件尚未创建；这里的书目目录只是命名示例，未选择任何实际书籍。

```text
reading-notes-content/
  README.md                 阅读入口与书目索引
  books/
    b001-short-title/
      note.md               书目信息、阅读问题、过程记录、全书回顾
      chapters/             内容需要拆分时再建
  topics/                   按需建立的跨书主题笔记
  inbox/                    尚未归入书目或主题的临时记录
  assets/                   按书目编号归档的图片等附件
  templates/                工作区启用后创建的正式笔记模板
  exports/                  按需要生成的分享或打印版本
```

书目编号保持稳定，例如 b001；不同版本或译本的出处在书目信息中写清。日期属于笔记内容，避免用每天的日期作为主要目录层级。临时记录在下一次整理时归入书目或主题；同一笔记维护一份当前正文，修改历史交给 Git。

## 笔记格式

建议使用 UTF-8 Markdown，正文以标题、列表、引用和普通链接为主。Markdown 是结构化文档的纯文本格式；采用较少扩展语法便于在不同编辑器中继续使用。[CommonMark 规范](https://spec.commonmark.org/spec)

每本书保留书名、作者、译者或版本、阅读状态和阅读目的。开始阶段允许资料暂缺并注明待补；涉及作者观点或摘录时，需要能够定位到相应版本、章节或页码。电子书可使用章节标题和位置号；扫描 PDF 区分文件页码与书中印刷页码。

每条重要记录区分三种内容：作者说了什么、我如何理解或质疑、哪些问题仍待验证。直接摘录使用引用块并附出处，转述明确写为作者观点，自己的推断写在个人思考中。若后续用 AI 辅助整理，应把待核实的补充与已从书中核对的内容区分开。

建议的最小记录单位是“出处 + 一个重要观点或观察 + 自己的回应”。阅读问题和全书回顾逐步补充，应用尝试、反例、关联阅读等作为可选项。文学类可以把论点栏改成叙事、人物或语言观察，仍保留出处与个人回应。

下面是格式约定示例，正式模板在业务工作区启用后创建。

```markdown
# 书名

- 作者及译者：
- 版本及阅读媒介：
- 阅读状态：计划读 / 在读 / 暂停 / 已读
- 阅读日期：
- 主题标签：按需要填写

## 我带着什么问题读这本书

写下最想理解的一个问题，以及已有的判断。

## 阅读记录

### 日期与章节

- 出处：版本、章节、页码或电子书位置
- 作者观点或作品观察：用自己的话概括
- 我的思考：理解、质疑、联想或反例
- 待验证的问题：按需要填写

> 必要的短摘录；另附具体出处。

## 全书回顾

- 这本书如何回应我的阅读问题
- 最值得保留的观点或阅读体验
- 我的理解发生了什么变化
- 仍未解决的问题与后续尝试

## 关联阅读

按需要链接到其他书目或主题笔记。
```

日常记录以便于继续阅读为准，不预设每章字数或要求所有栏目填满。阶段回顾能说明读到了哪里、保留了什么、还有什么疑问即可；“已读”只是阅读状态，成果是否通过确认仍按项目任务约定处理。

独立仓库拟使用框架同级目录 ../reading-notes-content，本机默认位置对应 C:/Users/YinZh/Documents/workspace/reading-notes-content，主线建议 main。它是待确认的路径提案，并非已存在或已获写入授权的工作区。Git 可以在本地初始化仓库，远程托管并非开始记录的必要条件。[Git 官方 git-init 文档](https://git-scm.com/docs/git-init)

建议先本地使用；如需要跨设备或异地备份，再选择私有远程仓库并确认服务和同步方式。Git 提交保存本地修改历史，异地备份另行安排。WORKSPACE 启用 git 前必须填入可核实的 repository 标识、branch、完整 revision 和可移植 checkout；尚无真实仓库与提交时继续保留 none，不填示例地址或虚构哈希。仅本地仓库时，repository 标识的填写由超级管理员结合实际布局核对。

笔记正文、临时素材、正式模板、附件与导出物位于成果物仓库；本方案、任务、决定、评审与验收记录位于 OPC。OPC 成果索引通过“仓库 + 仓库内路径 + 最终合并提交”引用业务成果，避免在两个仓库重复存放同一份笔记正文。这一边界依据 [配置规范](../../../CONFIG_SCHEMA.md) 与 [项目运行协议](../../../PROJECT_PROTOCOL.md)。

Markdown 编辑器可以沿用当前习惯。若偏好笔记界面，可用 Obsidian 打开成果物目录；它把笔记保存为本地目录中的 Markdown 文件，并允许其他文本编辑器访问这些文件。编辑器选择不改变笔记正文的存储约定。[Obsidian 官方存储说明](https://obsidian.md/help/data-storage)

## 阅读与交付安排

用户记录阅读体验和个人判断，项目经理在 scope 内整理阅读计划、任务、阶段回顾安排及治理记录。后续如需由成员持续代写业务笔记或承担其他专业工作，先明确内容负责人及其授权范围；本方案不扩展当前项目经理身份。

任务按一册书或一个可检查的阅读阶段组织，日常每一条笔记无需单独登记任务。涉及业务成果更新时，按根分支策略在相应 feature 或 bugfix 分支处理，阶段完成后验证、合并并登记精确版本，再结束本轮。笔记可以先形成阶段成果，书的阅读状态继续为在读。

建议先用一本书试行，检查三个问题：记录是否妨碍阅读，是否能回找到原文，回顾时是否能看见自己的思考。试行后调整模板，再考虑更多主题分类、自动索引或导出排版。试行书目、时长和完成条件在首批书目确定时约定，本轮不预设。
