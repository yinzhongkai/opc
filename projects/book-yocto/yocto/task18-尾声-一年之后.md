# 尾声　一年之后

## 1. 又一年

周一上午九点，三楼大会议室。

投影上的标题换了——"falcon 项目启动会"。阿凯坐在台前，面前是自己做的幻灯片。一年前他坐在靠后的位置，捏着没拆封的工牌，听别人宣布 tiger 项目启动；今天轮到他站起来，给一屋子人讲 falcon 的 BSP 方案。

会开始之前，老吴先翻了两页 tiger 的复盘。tiger 量产满一年了。两页幻灯片，每件事一句话：板子回片那天，在虚拟板上搭好、验证过的整套固件刷上真板子，一次点亮——老周在序章里说的那句"如果前面虚拟板这关把得严，真板子这步就不会有太多惊吓"，原样应验；OTA 上个月真推了一轮，现场没出乱子，倒是推完之后客户那边有人来问了三句话，这个故事待会儿讲。

老周还是坐在角落，面前的笔记本还是一个字没记。不同的是，阿凯已经不用天天去找他了。

## 2. falcon 的第一课

散会后，falcon 组刚来的新人跟着阿凯回工位，手里拿着刚领的工牌——封套没拆。阿凯看着那个封套，笑了一下，从抽屉里抽出一张白纸。

"先别急着碰板子——板子也没回来。"他把这句话原样送给了新人，然后在纸上画了三个框：造板、搭栈、回片验证。"这几个月你都在这条线上。今天你先知道有这么个地图就行。"

地图的内容没变，走路的人换了。这是这张地图第一次换手。

falcon 的 BSP 落地形态，正好兑现 chapter 12 老周那句"架构搭对了，后面复用就是配一个新 MACHINE 的事"。阿凯带着新人把账本翻了一遍：

- **新写的只有一份 Machine 配置**——falcon 这块板的硬件事实，照 tiger-aarch64.conf 的分段结构写，每段都能说出是哪一章加的，每行都要能回答"这行回答什么问题"；
- **Distro 配置原样复用**——发行版策略不因换板子改变，tiger-distro 的两态结构直接继承；
- **CI 流水线复制一份改几个值**——chapter 13 那份 YAML 里 MACHINE、DISTRO、IMAGE 本来就是参数，当时的 💡 框说"falcon 项目来的时候，复制这份 YAML 改几个值就是它的流水线"，今天就是"来的时候"；
- **发布证据链模板照搬**——层基线怎么记、SRCREV 表怎么填、MANIFEST 什么格式，chapter 16 那套东西原样拿走。老周当时说"falcon 项目明年第一天就用得上"，一字不差。

"所以我要先把 Yocto 整个学一遍吗？"新人问。

"不用。"阿凯听见自己说出了和老周一模一样的答案，"你回去第一件事——别碰板子、别碰仓库——把 Yocto 在你自己机器上装起来，从头跑一遍，构建出一个最小的、能开机进命令行的系统……跑通了，我们再聊下一步。"

真正要新做的只有"这块板子是什么"；剩下的全是复用。阿凯合上白纸的时候意识到，这就是"架构搭对"的利息——它不是省一次力气，是每来一个新项目就再付一次息。

## 3. OTA 那一天

tiger 真推 OTA 是上个月的事。升级流程本身——怎么写另一套、怎么改指针、起不来怎么回滚——是产品功能层的设计，本书从 chapter 9 起就没展开，今天也不展开。值得讲的是另一件事：这条产线依赖的每一样东西，都是这本书里造出来的。

最底下是 A/B 分区。chapter 7 的 boot.cmd 里那段 `if test "${bootpart}" = "b"` 的判断，当时是"交付的是打包形态、执行语义是伏笔"的骨架；chapter 9 它落成 NAND 上的分区布局——rootfs_a / rootfs_b 两套卷的位置、env 段里那个等被改写的 `bootpart`；到 chapter 10 总装，两套卷才真正建起来。从 chapter 7 备到现在的产线，上个月终于服役。推送那晚阿凯盯着监控，看设备一批批从 A 面切到 B 面、零星几台起不来的又自动指回 A 面——心里想的却是 chapter 7 那个下午写骨架时落下的那句话："今天这个 `if` 就是它的雏形。"原来"雏形"这个词，是这个意思。

推送之后一周，客户那边有人来问。不是事故，是例行的安全审查，但问题还是那三句——chapter 16 引子里那个事故的三句，也是老周当堂考过阿凯的三句：

"这版系统里装了什么？"——license.manifest 给人看，SBOM 给机器看，逐包在列。

"它是从哪些源码造出来的？"——MANIFEST 前半页，三个层的基线提交、四个组件的 SRCREV 或 tarball 基线，源码归档的介质编号登记在案。

"里面有没有还没回上游的修改？"——MANIFEST 后半页，patch 表，每个 patch 的 Upstream-Status 一行一行写得清楚。

三句话，三分钟答完。对照组在 chapter 16 的引子里：当年那个现场，三句"我查一下"，查了一个星期。放下电话，阿凯想起老周在发布那天的最后一句话——"等 tiger 真推 OTA 那天，现场再问出这三句话——你会感谢今天。"

他确实感谢。

## 4. 那个 patch 的归宿

这一年里的一次内核升级，阿凯在 meta-tiger 的 `recipes-kernel/linux/linux-tiger/` 目录里又看到了那个熟悉的长文件名——看门狗差一修复的那个 patch。他忽然意识到一件事，拎着笔记本去找老周。

"那个 patch，后来在咱们这层里养了一年了。它的结局到底什么样？"

老周没回答，抬了抬下巴："你先翻翻那个目录，告诉我它现在什么样。"

"还在。`Upstream-Status` 还是 `Pending`。"阿凯翻开 patch 头部确认了一眼。这行字一年没变过——原因本书在 chapter 15 交过底：tiger 是虚构硬件，那封提交信永远停在草稿箱，本书的世界线里它不会被真发出去。所以这本书里，这个 patch 永远停在 Pending。这是诚实边界，不是烂尾。

但"停在 Pending"不等于躺着不动。这一年 linux-tiger 跟进过几次 6.6.x 点版本，每次 bump SRCREV，先拿这个 patch 对新基线过一遍堂——打得上就翻篇；赶上上游动了邻近行、do_patch 报 FAILED，才走 chapter 15 那套门：摘掉哑弹、开工作区、`git am -3` 重放、finish 刷新。chapter 13 立的哨兵也一直盯着上游的动静。养一个 patch 的日常，阿凯已经做得像呼吸一样自然。

"真项目里呢？"他追问，"如果那天我真按下了发送键。"

"那它这会儿该随某个 6.6.y 回来了。"老周说，"到那天你再 bump SRCREV，do_patch 会先给你报一次 FAILED——因为你的修改已经在基线里了，patch 里记的上下文成了多余。别慌，那不是坏消息，是讣告。把 SRC_URI 里那行 file:// 摘掉，patch 文件删掉，提交——就是它寿终正寝的那一笔。"

"所以一个 patch 的终点不是被上游合并，"阿凯慢慢说，"是被我亲手从自己层里删掉。"

"合并是上游的事，删除是你的事。"老周点头，"Pending 改成 Submitted 是一跳，随上游新版本回归是一跳，删掉它是最后一跳——每一跳都得有人盯着。上游跟踪不是一锤子买卖，是常态。meta-tiger 里每个 patch 头上那行 Upstream-Status，就是你盯梢的账本。"

阿凯回去后翻了翻 meta-tiger 里的另外三个 patch——三个 `Inappropriate` 的 tiger 硬件 patch，永远不上游，也永远有人认得它们为什么在那里。账本还薄，但格式已经立住了。

## 5. 我教你的不是 Yocto

复盘会开完的那个周五，下班前老周把阿凯叫住了。他难得主动开口。

"一年了。有句话今天可以说了。"老周往椅背上一靠，"**我教你的不是 Yocto，是怎么做 BSP。Yocto 会变，但工作方法不会。**"

"会变？"阿凯问，"变成什么样？"

"你自己就见过。"老周掰着指头，"发布那天踩的那个坑——老教程里满坑满谷的 `*GPL-3.0*` 写法，4.0 起成了非法通配符，变量还在，取值语法变了。还有可重现构建，早年间要手动开一个开关才有，后来开关默认就开着，4.0 起连开关带专门的类一起移除了——不是能力没了，是它成了本体。往后 Scarthgap 之后的版本还会迭代，变量还会改名，类还会消亡。你五年后回头看今天记的这些命令，一半可能变了样。"

"那什么不会变？"

"三样东西。"老周说。

**第一样，工程组织。** 序章里那张白纸上的竖线——开发态和集成态分开——是全书第一颗钉子。然后 chapter 3 搭起 meta-tiger 的骨架、定下 4+1 仓库的格局（四个开发态组件仓库，加 meta-tiger 这个集成层，poky 不算）；chapter 4、6、7，一律 bbappend 叠加，不动上游配方一行；chapter 7 就立过"仓库动一次，SRCREV 跟一次"的纪律，chapter 8 和 9 内核改动必回 linux-tiger 仓库提交再 bump SRCREV。说到底是一句话：每样资产有且只有一个家，任何人看到目录就知道东西该放哪。

**第二样，边界感。** chapter 2 阿凯在 MACHINE 配置里写 `DISTRO_FEATURES += "systemd"`，BitBake 不报错，变量真改了——但那是越界，不是生效。chapter 5 注释掉占位行，报错消失了——问题没被解决，是被藏回了 linux-dummy 的空壳里。chapter 14 和 15，devtool 工作区是开发区，finish 才把修改收回层里。这条线的教训也是一句话：工具不拦你的地方，正是纪律要站岗的地方。

**第三样，合规闭环。** chapter 13 让 CI 和 buildhistory 每次构建自动记账；chapter 15 给 patch 带上 Signed-off-by 和 Upstream-Status，让每处未进上游的修改都有履历；chapter 16 把版本固定、源码归档、license 清单、SBOM、可重现证明收拢成证据链，发布那天 OTA 三问当场答出。这条线的要点在于：合规不是发布会前补材料，是每天顺手记账，发布那天只是把账本装订成册。

"这三样，跟 Yocto 没有关系。"老周收尾，"换个构建系统，换个芯片平台，换个公司，它们还是对的。Yocto 只是它们眼下最好的载体——所以值得你认真学，但不值得你把方法当成工具本身。"

## 6. 写在最后：给读者

阿凯的故事讲到这儿。接下来的几段，是作者直接写给你的——四条收尾的指引。

### 6.1 继续学 Yocto 的路径

- **把本书的对照实验法用下去**：改一个变量、跑一遍 `bitbake -e`、对比前后输出；存一份构建、换个干净目录再构建、比对哈希。这套手法离开这本书照样好用——它是你在任何版本、任何项目里自己找答案的通用工具。
- **把变量术语表当字典，不当教程**：遇到不认识的变量去查它的条目，比从头通读文档有效得多。地址见章末延伸阅读。
- **跑一次 oe-selftest**：Yocto 官方用例库自己测自己的方式。看看上游怎么设计验证，是校准"什么叫测到位"的最好参照。
- **跟迁移指南做一次升级演练**：挑相邻两个版本，把迁移指南逐条对进自己的层——哪些写法废止了、哪些默认值改了。一遍下来，比读十篇博客扎实。
- **读官方层的惯例**：meta-arm、OE-Core 里的配方和 bbappend 是最好的范文。chapter 6/7 里"找现成配方、再把它读懂"的取证手法，用在任何陌生层上都成立。

### 6.2 社区资源

- **Yocto 项目文档站**：本书全部技术声明的对照来源，按版本号分册，查 Scarthgap 就锁定 5.0。
- **Yocto Project 邮件列表**：项目级问题的讨论现场，提问前先在存档里搜一遍。
- **OE-Core 邮件列表**：往下一层的列表，OE-Core 的配方和类的改动在这里讨论。
- **Yocto Project Wiki**：社区维护的百科式站点——工作组、活动、历史资料比文档站更全，也更杂。
- **Yocto Project Summit（YPS）**：Yocto 项目社区定期举办的在线技术大会——开发者讲实战、维护者讲路线图，录像和讲稿公开。
- **lore**：内核侧的邮件存档站，chapter 15 找 patch 存档链接的地方。
- **LWN.net**：Linux 内核开发动态的深度报道，适合长期跟踪。

### 6.3 推荐阅读

- *Embedded Linux Primer*（Christopher Hallinan）：嵌入式 Linux 的全景背景读物——启动链、存储、调试各章，补这本书没展开的底色。
- *Mastering Embedded Linux Programming*（Frank Vasquez 与 Chris Simmonds；第 4 版起更名 *Mastering Embedded Linux Development*）：与本书互补的深入路线，启动链和文件系统讲得更细，Buildroot 与 Yocto 两条线都有。
- *Embedded Linux Systems with the Yocto Project*（Rudolf J. Streif）：市面上少有的 Yocto 专著，按概念域组织——本书给你走完一个项目，它给你把每个概念摊开。

### 6.4 把这套工作流带回你的项目

本书的工作流可以整套搬走：4+1 仓库组织（组件仓库各归各家、集成层只管拼装）、bbappend 纪律（不动上游配方）、patch 生命周期表（每个 patch 一行 Upstream-Status）、发布证据链模板（MANIFEST + 五件 + 校验和）。你的板子不是 tiger，但这些表格的列名原样可用。

书后三篇附录是为三个具体场景备的工具：**附录 A** 给应用开发者——拿到 SDK 之后的速览，可以单独抽出来发给组里不写 BSP 的同事；**附录 B** 给下一任 BSP 工程师——阿凯去带 falcon 之后，接手 meta-tiger 的人照着它就能上岗；**附录 C** 是全书命令的速查索引，适合打印出来贴在显示器边上——就是 chapter 5 里那句"值得贴在显示器边上"的那类东西。

## 7. 本章小结

尾声把全书开过的头一一收回：

- **三条叙事线**：falcon 落地——"配一个新 MACHINE 的事"实物兑现，地图第一次换手；OTA 真推了——chapter 7 的 boot.cmd 骨架服役，客户现场三问三分钟答出，"你会感谢今天"落地；回片验证——序章老周地图的第三个框，一次点亮，只交代结果。外加那个 patch 的归宿——本书诚实停在 Pending，生命周期最后一跳以真项目的样貌讲给你听。
- **三条方法论**：工程组织（每样资产有且只有一个家）、边界感（工具不拦你的地方，纪律站岗）、合规闭环（每天顺手记账，发布只是装订成册）。Yocto 会变，工作方法不会。
- **四类指引**：继续学的路径、社区资源、推荐阅读、工作流复用——入口都在第 6 节，URL 收在章末延伸阅读。

序章还有一条暗线今天正式揭盅：Buildroot 到底在哪撑不住？一年后再看，答案就是三件事——长期维护（OTA 就是它的第一课）、合规、可审计；而这三件，正是 tiger 后八章一章一章干出来的活。前言里"明确的边界感"和"发布合规与交付……不是选修课"两条承诺，也在这里交卷。

序章里那个在本子上写下"Yocto"并画了个问号的阿凯，如今成了给别人画地图的人。地图已经交到你手里——下一站，轮到你给别人画。

尾声不改 meta-tiger 的任何文件——这是 meta-tiger 自 chapter 3 建立以来的第一次：以往每章 tag 都跟着一笔新提交走，这次没有新提交可打，直接打在现有 HEAD 所指的提交上，作为全书的终点标记（它与 `chapter16` 指向同一个提交）。chapter 1 和 2 在 poky 里打 tag 时就是这么干的——没有交付改动的章，tag 就是一枚纯书签。

```bash
# 全书终点标记：本章无交付改动，tag 打在 meta-tiger 现有 HEAD 所指的提交上
cd ~/workspace/meta-tiger
git tag epilogue
```
