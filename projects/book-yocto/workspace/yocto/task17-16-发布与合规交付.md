### 16.1 版本固定：SRCREV 与层基线

#### 16.1.1 先审 SRCREV

第一件事阿凯已经会做了。chapter 6 集成 TF-A 时立过规矩：直拉 git 仓库的配方必须用 SRCREV 钉住一个具体提交，分支名是会动的指针。发布前先把 meta-tiger 里的声明全量过一遍：

```bash
# 全量审计：meta-tiger 里所有 SRCREV 声明
# （^ 锚住行首——注释行里也写着这三个字母，先滤掉噪音）
grep -rn "^SRCREV" ~/workspace/meta-tiger --include='*.bb' --include='*.bbappend'
```

输出（行号与公共路径前缀略）：

```text
recipes-bsp/trusted-firmware-a/trusted-firmware-a_%.bbappend:SRCREV_tfa = "8f3d2e1c7a9b4e5f6c0d1a2b3e4f5a6b7c8d9e0f"
recipes-bsp/u-boot/u-boot_%.bbappend:SRCREV = "0000000000000000000000000000000000000000"
recipes-kernel/linux/linux-tiger.bb:SRCREV = "0000000000000000000000000000000000000000"
```

（TF-A 一行是 chapter 6 的占位哈希，U-Boot 与内核两行是全零占位——都待各仓库就位后回填真实值，审计动作与结论不受影响。）

裸 grep 不带 `^` 会连注释行一起命中——chapter 8、9 的配方里，SRCREV 上方的注释也写着这三个字母。赋值行都顶格写，`^SRCREV` 一锚一个准。三家 git 直拉各锁一个提交，逐条 `bitbake -e <配方名> | grep ^SRCREV` 抽查终值与声明一致——单条查询的手法在 7.7.3 用过，这次是把它串成"全量审计"的发布动作。QEMU 不在名单里：它的基线是官方 8.2.7 发布 tarball 加 meta-tiger 里的三个 patch（4.3），锁版本靠 `PV` 与 tarball 校验和，不走 SRCREV——两种锁定形态都要认得。

> **⚠️ 注意**：审计时如果看到 `SRCREV = "${AUTOREV}"`，等于没锁——`AUTOREV` 是 BitBake 的特殊值，意思是"每次构建时取分支最新提交"，发布物里出现它，版本基线这一环直接断掉。日常开发有人图省事用它，发布审计见一个杀一个。

#### 16.1.2 "poky 自己的版本谁记？"——层基线

"锁完了。"阿凯宣布，"三个 SRCREV 都在。"

"配方里的锁住了。"老周点点头，然后问了一句，"poky 自己、meta-arm 自己的版本，谁记？"

阿凯愣住了。SRCREV 锁的是**配方拉取的组件源码**；可构建这版系统的不止组件——poky 的类文件、meta-arm 的配方、meta-tiger 自己，这些**层**的内容同样决定产物。层也在演进：三个月后 poky 的 scarthgap 分支又挪了几十笔提交，"同一份源码"这四个字本身就成了空话。

层基线没有现成变量可查，但每个层都是一个 git 仓库——仓库的版本基线就是提交哈希：

```bash
# 记录三个层的基线提交（发布时点的 HEAD）
git -C ~/workspace/poky rev-parse HEAD
git -C ~/workspace/meta-arm rev-parse HEAD
git -C ~/workspace/meta-tiger rev-parse HEAD
```

输出（以本地实际为准）：

```text
a1b2c3d4e5f6...（poky，scarthgap 分支发布时点 HEAD）
f6e5d4c3b2a1...（meta-arm，scarthgap 分支发布时点 HEAD）
<meta-tiger 的 HEAD——见下方说明>
```

三行值待会儿进 MANIFEST（16.6.2）。meta-tiger 那行有个先有鸡还是先有蛋的问题：本章的 distro 配置改动还没提交（16.2.3 会给 tiger-distro-prod.conf 追加一行 INHERIT），HEAD 此刻不是终态——所以 meta-tiger 的基线不记哈希，记**本章末尾要打的 tag 名** `chapter16`，tag 名比哈希好读，指向的还是同一个提交。另外，13.5 启用的 buildhistory 每次构建都会把各层的分支与提交自动写进 `buildhistory/metadata-revs`——手工这三行是给 MANIFEST 落纸，buildhistory 那份是自动底账，两个来源互为印证。

#### 16.1.3 patch 清单进证据链

15.6.3 老周撂过一句话：发布的时候，meta-tiger 里每个 patch 的清单、每个 Upstream-Status 的取值，都要跟着 SRCREV 一起进证据链。现在兑现。一条 grep 收全：

```bash

grep -rn "Upstream-Status" ~/workspace/meta-tiger --include='*.patch'
```

输出（关键行，行号与公共路径前缀略）：


整理成表——这张表就是"这版系统里有哪些没进上游的修改"的标准答案：

| patch 文件 | 干什么 | Upstream-Status |
|-----------|--------|-----------------|
| `0001-hw-arm-Add-tiger-machine-skeleton.patch` | QEMU tiger machine 骨架 | `Inappropriate`（虚构硬件，不上游） |

前三个 `Inappropriate` 是 4.4.2 就标好的——tiger 是虚构硬件，永远不会提交上游，这不是欠账。最后一行是 chapter 15 那个 watchdog 修复，本书停在 `Pending`（15.5 只走到 dry-run）：它第一次进发布物，身份是"已修好、待提交"。真项目里这张表评审要逐行过——每个 `Pending` 都得有人认领"为什么还没发"。

#### 16.1.4 切到发布态

最后一个小动作：发布构建用 prod 态。11.6 分家的纪律是 local.conf 里改一行：

验完**不回切**——从本章起主构建目录停在 prod。两态的行为差异（优化档、debug-tweaks 缺席、read-only-rootfs）在 11.8 的表里对过账，这里不重复。11.9.2 量过的老教训再记一遍，只是这回机理要细分：三元组**不动**（`TARGET_VENDOR = "-tiger"` 在公共基座 tiger-distro.conf，dev/prod 两态同为 `aarch64-tiger-linux`），翻任务签名的是 `DEBUG_BUILD`/`SELECTED_OPTIMIZATION` 优化档、debug-tweaks 缺席、read-only-rootfs 这一族——签名一翻，sstate 命中照样崩塌，prod 态首次构建按近全量预期：小时级，先去泡杯茶。

### 16.2 archiver class：把源码归档下来

#### 16.2.1 清单 ≠ 归档：GPL 的随附源码义务

"license 的事 chapter 11 不是弄过了吗？"阿凯翻出笔记，"11.7 立了门槛。"

"11.7 立的是**放进来的门槛**。"老周说，"今天要解决的是**发出去的义务**。GPL 族组件随产品分发，许可证条款要求随附（或书面提供获取途径）对应的源码——不是你仓库里有就行，是要能交付给对方。清单只是一张表，表不能当源码使。"

> **⚠️ 注意**：这里钉死一个分工，后面 16.3 不再混淆——license.manifest 回答"装了什么、什么许可"，是**清单**；archiver 回答"源码在哪、拿得出来"，是**归档**。清单 ≠ 归档，两手都要硬。

#### 16.2.2 机制：archiver.bbclass 与默认过滤器

Yocto 的归档机制是一个类：**源码归档类（archiver.bbclass）**——全局继承后，为构建链上的每个配方把源码打成 tar 包收进 deploy 目录。先看它的出厂设置：

```bitbake
# 文件路径：~/workspace/poky/meta/classes/archiver.bbclass（节选）
# 头部注释（第 8-26 行）列出的归档模式：
#  1) original（未打补丁的原始源码）
#  2) patched（打完补丁的源码，默认）
#  3) configured（配置完成的源码）
#  4) mirror（源码镜像）
#  9) license 过滤：COPYLEFT_LICENSE_INCLUDE 命中才归档，
#     COPYLEFT_LICENSE_EXCLUDE 命中则排除

ARCHIVER_MODE[src] ?= "patched"            # 第 52 行
ARCHIVER_MODE[diff] ?= "0"                 # 第 53 行
ARCHIVER_MODE[compression] ?= "xz"         # 第 58 行
DEPLOY_DIR_SRC ?= "${DEPLOY_DIR}/sources"  # 第 60 行
```

默认值每一行都值得认一遍。`patched` 模式归档的是**打完补丁之后**的源码树——meta-tiger 的 patch 都在里面，正好是"造这版二进制实际所用的源码"，合规语义上最省事。压缩默认 xz。输出落在 `tmp/deploy/sources/` 下，再按 `${TARGET_SYS}/${PF}` 分目录（第 62-63 行：aarch64-tiger-linux / 配方名-版本-修订 两级）。

过滤器是另一个关键设计。archiver 继承 copyleft_filter.bbclass，后者的默认值：

```bitbake
# 文件路径：~/workspace/poky/meta/classes/copyleft_filter.bbclass（节选，第 13-17 行）
COPYLEFT_LICENSE_INCLUDE ?= 'GPL* LGPL* AGPL*'
COPYLEFT_LICENSE_EXCLUDE ?= 'CLOSED Proprietary'
```

也就是说**默认只归档 copyleft 族的源码**——GPL/LGPL/AGPL 命中的配方才归档，MIT/BSD 一族不进。这不是偷工减料：随附源码义务本就落在 copyleft 许可证头上，过滤器把归档范围对准义务范围。想全量归档（整树快照另作审计用），把 `COPYLEFT_LICENSE_INCLUDE` 放开成 `'*'` 就是，但体积代价自负——全量 sources 归档是数十 GB 量级的事。

#### 16.2.3 落点与构建

继承写在哪？阿凯的裁决：落 `tiger-distro-prod.conf`——**prod 即发布态**，归档的开销（耗时 + 磁盘）只让发布构建背，dev 态日常迭代不背。落点跟 13.5 的 buildhistory 正好是个对照：buildhistory 两态都要记账，当年落了 base；归档只有发布构建需要，落 prod delta——同一套"谁需要谁背"的裁决，两处各自选边。

```bitbake
# 文件路径：~/workspace/meta-tiger/conf/distro/tiger-distro-prod.conf（追加）
# 发布合规（16.2）：copyleft 族源码归档，随发布态走
INHERIT += "archiver"
```

阿凯顺手想把 SBOM 的 `create-spdx` 也写进去，老周拦了一句："先查查它是不是已经在了。"查到的结果 16.4.2 揭晓——这一行先不写。

> **🔥 重要**：无论这类开关落在哪个文件，发布构建所用的配置必须进版本库、能随 tag 复现。distro conf 在 meta-tiger 里，天然满足；要是图方便写进 local.conf 就发布，证据链断在"配置没存下来"这一环。

发布构建开跑：

```bash

cd ~/workspace/poky
source oe-init-build-env ../build

# prod 态重跑总装：deploy 里的 ubifs 已换代，总装件 tiger-nand-full.img 跟着换新
```

总装这一步不能省——上一次跑 mknandimg.sh 还是 15.8 章末（dev 态），不重跑的话，16.6.1 拷进发布包的 `tiger-nand-full.img` 就是 dev 态旧件，跟同包的 prod 态 ubifs 并排，镜像件内部自相矛盾。

构建完成后看归档产物（层级形态以实测为准）：


### 16.3 license 清单：license.manifest 与合规审计

#### 16.3.1 门槛与清单的分工

11.7 的两行注释态门槛（`LICENSE_FLAGS_ACCEPTED` / `INCOMPATIBLE_LICENSE`）管的是"放不放进来"；这一节管的是"发出去的清单"——镜像里每个包叫什么、什么版本、什么许可，落成一份文本，随发布物走。这份清单就是 **许可证清单（license.manifest）**。

生成不用动手：license.bbclass 第 262 行 `IMAGE_CLASSES:append = " license_image"` 给所有镜像配方全局挂上了 license_image.bbclass，它的 `license_create_manifest` 函数挂在 rootfs 后处理阶段（该类第 297 行）——**每次镜像构建都自动产出**，从 chapter 1 第一次构建起它就一直在那里，只是今天才第一次当交付物看。

#### 16.3.2 产物认读

```bash
# license 产物目录：tmp/deploy/licenses/ 下按 pkgarch / 镜像名分目录
ls ~/workspace/build/tmp/deploy/licenses/
ls -l ~/workspace/build/tmp/deploy/licenses/tiger_aarch64/
head -20 ~/workspace/build/tmp/deploy/licenses/tiger_aarch64/tiger-image-tiger-aarch64.rootfs/license.manifest
```

输出（示意，以实测为准）：

```text
all  cortexa53  native  tiger_aarch64

tiger-image-tiger-aarch64.rootfs-20260902153041/
tiger-image-tiger-aarch64.rootfs -> tiger-image-tiger-aarch64.rootfs-20260902153041

PACKAGE NAME: acl
PACKAGE VERSION: 2.3.2
RECIPE NAME: acl
LICENSE: GPL-2.0-or-later

PACKAGE NAME: attr
PACKAGE VERSION: 2.5.1
RECIPE NAME: attr
LICENSE: GPL-2.0-or-later
# ...（每个包四行一段，按包名字典序）
```

逐列认：`PACKAGE NAME` 是运行时包名（ipk 粒度），`RECIPE NAME` 是它出自哪个配方，`LICENSE` 是**包级**的许可证表达式——`LICENSE:${PN}` 能覆盖配方级声明：acl 配方级写的是 `LGPL-2.1-or-later & GPL-2.0-or-later`，acl 包本体领 GPL-2.0 那一半，`libacl` 包才是 LGPL 那一半（acl_2.3.2.bb 第 10-12 行），manifest 里按包各记各的。

路径段也有两处认门：机器段是 `tiger_aarch64`（下划线——`MACHINE_ARCH` 会把连字符换成下划线，bitbake.conf 第 187 行）；顶层的 `native` 段是 native/cross 配方统一映射的结果（license.bbclass 第 21-23 行），没有 `x86_64-linux`。顺带认一下顶层 `all` 段：allarch 配方的 `PACKAGE_ARCH` 被改写为 `all`（allarch.bbclass 第 18 行）落在这里——注意这跟 16.2 源码归档里的 `allarch` 目录是两套机制，archiver 那边是强制命名的目录名（archiver.bbclass 第 116 行），别混。时间戳目录加裸名软链的命名法跟镜像产物同一套（12.1.4 的 IMAGE_LINK_NAME 机制在 license 目录也生效——注意 `.rootfs` 段在时间戳**之前**）。同目录还有两份姊妹文件：`package.manifest`（纯包名版本清单）和 `image_license.manifest`（bootloader 等 deploy 件的许可清单——TF-A、U-Boot 这些不进 rootfs 但进交付物的孩子归它管）。

默认清单只落在构建机。`COPY_LIC_MANIFEST = "1"` 可以把清单拷进镜像的 `/usr/share/common-licenses/`（licenses.conf 第 120-125 行注释态），`COPY_LIC_DIRS = "1"` 连许可文本一起拷——板上自带合规信息是有些产品的要求，tiger 暂不开启，知道开关在哪即可。

#### 16.3.3 审计实操：对着门槛对账

清单在手，审计就是 grep。11.7 那两行注释态门槛——`LICENSE_FLAGS_ACCEPTED = "commercial"` 与 `INCOMPATIBLE_LICENSE = "*GPL-3.0*"`——如果哪天法务要放开，会拦到谁、放到谁？对账前先钉个伏笔：那行注释的取值 `*GPL-3.0*` 其实是老教程传下来的写法，Scarthgap 已经不认——怎么个不认法，16.7.1 的坑 1 会当场演出来。本节只做对账，按"假如门槛以合法形态放开"来算：

```bash
# 假设放开 GPLv3 排除：今天会拦到哪些包？
```

### 16.4 SBOM：给机器看的物料清单

#### 16.4.1 阿凯之问：跟 license.manifest 不是一回事吗

"等下。"阿凯举手，"SBOM 和 license.manifest 不是一回事吗？都是'装了什么'的清单。"

"问到一个点子上了。"老周说，"license.manifest 是**给人看的表**——纯文本，包名版本许可四列。SBOM 是**给机器和审计工具看的图**——**软件物料清单（SBOM）**，记录产品里每个组件的名称、版本、许可、来源、以及组件之间的关系，格式标准化，漏洞扫描器、合规审计工具直接吃。客户的安全团队拿到镜像，第一件事是拿 SBOM 去撞 CVE 库——'你们这版的 openssl 是不是受影响那个版本'，机器比对，不用翻文本。"

**软件包数据交换（SPDX）**是 SBOM 的主流标准格式之一（Linux 基金会主持），Yocto 生成 SBOM 走的就是它。一句话分工：manifest 回答人的问题，SBOM 回答机器的问题，两个都要。

#### 16.4.2 机制：create-spdx 与 SPDX 2.2

生成机制同样是一个类。但阿凯照着 16.2 的老路准备写 `INHERIT += "create-spdx"` 之前，先办了老周让办的事——查它是不是已经在了。答案在 poky 自己的配置里：

```bitbake
# 文件路径：~/workspace/poky/meta/conf/distro/defaultsetup.conf（节选，第 17-18 行）
INHERIT_DISTRO ?= "debian devshell sstate license remove-libtool create-spdx"
INHERIT += "${PACKAGE_CLASSES} ${USER_CLASSES} ${INHERIT_DISTRO}"
```

`defaultsetup.conf` 由 bitbake.conf 第 832 行无条件 include，任何 distro 都吃这份默认；tiger-distro 从没覆盖过 `INHERIT_DISTRO`，所以 `create-spdx` **从 chapter 1 第一次构建起就一直在继承链上**。SBOM 跟 license.manifest 是同一类产物——不是本章开启的，是一直在产出、今天第一次当交付物看。本章的动作因此不是"开启"，是三步：发现它一直在产出、认识内容、纳入证据链。（用 poky 发行版的日子里它甚至有双保险——poky.conf 第 84 行另写了一份 `INHERIT += "create-spdx"`。）

再看类本身。`create-spdx.bbclass` 全文只有八行，正文就一行 `inherit create-spdx-2.2`，注释写明"不在乎具体版本就继承我，我会指向当前支持的最新稳定版"。Scarthgap 里它指向 SPDX 2.2：

```bitbake
# 文件路径：~/workspace/poky/meta/classes/create-spdx-2.2.bbclass（节选，第 7-9 行）
SPDX_VERSION = "2.2"                                    # 第 7 行
DEPLOY_DIR_SPDX ??= "${DEPLOY_DIR}/spdx/${SPDX_VERSION}" # 第 9 行
```

挂接方式与 archiver 同款：`do_rootfs[recrdeptask] += "do_create_spdx do_create_runtime_spdx"`（第 960 行）——镜像构建时，依赖链上每个配方各出一份配方级 SPDX 文档（外加按包、按运行时依赖的姊妹文档），rootfs 后处理阶段再由 `image_combine_spdx`（第 963 行挂接）汇成镜像级文档。SDK 通道有同款挂接（第 965 行 `do_populate_sdk[recrdeptask]`）——16.3.3 说的"SDK 的 SBOM 早有产出"就是这一行。

> **💡 提示**：同目录还躺着一个 `create-spdx-3.0.bbclass`（SPDX 3.0.1，第 9 行）——Scarthgap 已引入 SPDX 3.0 支持，但默认仍走 2.2。本书用默认；要尝 3.0，姿势是两步：`INHERIT_DISTRO:remove = "create-spdx"` 再 `INHERIT_DISTRO:append = " create-spdx-3.0"`——只加不除会让两个版本的类同时生效。哪天想彻底关掉 SBOM，同理 `INHERIT_DISTRO:remove = "create-spdx"` 即可。

#### 16.4.3 产物查看与轻量消费

### 16.5 可重现构建：锁了源码不等于锁了构建

#### 16.5.1 Scarthgap 的内建机制：SOURCE_DATE_EPOCH

前四件证据齐了，老周却问了个新问题："16.1 锁了版本基线。三个月后审计拿着你的 MANIFEST，checkout 同一批提交，构建一次——产物跟你发布的那个，是同一个东西吗？"

阿凯下意识想答"是"，又刹住了："……不一定。构建过程里有时间戳、有路径，这些东西每次都变。"

"对。**锁源 ≠ 锁构建**。"老周写下四个字，"证据链的最后一环，是**可重现构建（Reproducible Build）**——同一份元数据构建两次，产物逐字节相同。前面章节里'可重现'三个字出现过好几回（6.5.2 的 SRCREV 注释就写着它），今天正式落地。"

先纠正一个阿凯刚从旧教程里看来的认知：他本来打算找"可重现构建的开关"，在 Scarthgap 里找不到——**没有开关，因为不需要**。可重现构建自 Yocto 3.1 起默认开启，Scarthgap 里它是一组内建机制：

```bitbake
# 文件路径：~/workspace/poky/meta/conf/bitbake.conf（节选，第 685-687 行）
export SOURCE_DATE_EPOCH ?= "${@get_source_date_epoch_value(d)}"  # 第 685 行
SOURCE_DATE_EPOCH_FALLBACK ??= "1302044400"                        # 第 687 行

# 文件路径：~/workspace/poky/meta/classes-global/base.bbclass（节选，第 203/210 行）
do_unpack[postfuncs] += "create_source_date_epoch_stamp"           # 第 210 行
addtask do_deploy_source_date_epoch before do_configure after do_patch  # 第 203 行
```

核心变量就地解释：`SOURCE_DATE_EPOCH`——可重现构建社区的标准约定，一个 Unix 时间戳，构建工具见到它就**以它代替"当前时间"**写进产物。BitBake 在每个配方解包后自动推导它（meta/lib/oe/reproducible.py）：git 源码取**最后一次提交的时间戳**（第 102-120 行）——源码锁定，时间戳也就锁定；tarball 则取解包树内**最新文件的修改时间**（第 122-148 行）；都找不到就用 FALLBACK 常量（第 150-156 行）。

认这个变量的落点是一整条链：内核（kernel.bbclass 第 364-373 行的构建时间戳）、打包、SDK（populate_sdk_base.bbclass 的 tar `--clamp-mtime`）各处都认它。文件名时间戳也有同款推导（image-artifact-names.bbclass 第 36-41 行），但注意前提——它只对继承 deploy 类的产物生效（kernel、U-Boot 一路）；**镜像配方不继承 deploy 类，镜像文件名里的时间戳段仍是墙钟**。这个差别 16.5.3 比对时还要回来认账。

除了时间戳，还有一整族配套：`DEBUG_PREFIX_MAP`（把编译路径从产物里抹平）、`HOSTTOOLS`（管住配方能调用哪些宿主机命令）——两个新名词认得即可；PACKAGECONFIG 显式化（12.2.3 立过的纪律）、recipe-sysroot 隔离（14.1.1 见过实物）是前文史。回头看，那些章节里看似琐碎的纪律，很多都是可重现性的地基。

> **⚠️ 注意**：默认开启 ≠ 保证达成。官方口径（测试手册原话）：只有 BitBake 与 OE-Core 保证完全可重现，**你往构建里加的每一个层，都可能把这份保证打破**——meta-tiger 的配方写的任何东西，都在保证范围之外。所以这一节的主线不是"开启"，是"确认 + 验证"：确认机制在位，然后亲手验证一次给审计看。

#### 16.5.2 "你怎么证明给别人看？"——实验设计

"机制我认了。"阿凯说，"反正默认就是开的，这环算焊上了？"

"你怎么证明给别人看？"老周反问，"审计不认'默认开启'四个字，认的是你构建两次、哈希并排。实验设计你自己来。"

阿凯在白板上推了一遍：同一构建目录跑两次不行——第二次全是 sstate 命中，产物相同只证明"缓存忠实"，证明不了"可重现"。真正的考题是：**缓存没有了，还能不能造出一模一样的东西。**设计定稿：

1. 第一遍：16.2 那次发布构建的产物，记 sha256 基线。
2. 第二遍：**另起一个构建目录**，downloads 共享（源码是同一份）、sstate 不共享（全新空目录）、配置从主目录拷贝——从零重建 tiger-image。
3. 两边的 deploy 产物 sha256 并排比对，逐字节相同才算过。

#### 16.5.3 实验执行

```bash
# 第一步：主构建目录的发布产物记基线（用稳定软链名引用，mknandimg.sh 一路都这么引）
cd ~/workspace/build
sha256sum tmp/deploy/images/tiger-aarch64/tiger-image-tiger-aarch64.rootfs.ubifs \
    | tee /tmp/repro-main.txt

# 第二步：另起验证构建目录（downloads 共享，sstate 全新）
cd ~/workspace/poky
source oe-init-build-env ../build-repro
cp ../build/conf/local.conf ../build/conf/bblayers.conf conf/

# 拷过来必须改一行：DL_DIR 原值是 TOPDIR 相对值（1.3.2 设的），原样拷进新目录
# 就指到 build-repro 自己的空 downloads 了——改成主目录的绝对路径，源码才是同一份
# （11.8.2 建 build-distrotest 时指共享缓存，也是这样手工指了一次）
sed -i 's|^DL_DIR = "${TOPDIR}/downloads"|DL_DIR = "${HOME}/workspace/build/downloads"|' conf/local.conf
# SSTATE_DIR 那行不动：同为 TOPDIR 相对值，正好给新目录一个空 sstate——这正是实验要考的

# 从零重建（无 sstate 可用，预计数小时——发布验证动作，跑一晚上是它的常态）
bitbake tiger-image

# 第三步：并排比对（两边引的都是稳定软链名，文件名天然一致；awk 只取第一列哈希，防路径等杂项差异）
sha256sum tmp/deploy/images/tiger-aarch64/tiger-image-tiger-aarch64.rootfs.ubifs \
    | tee /tmp/repro-second.txt
diff <(awk '{print $1}' /tmp/repro-main.txt) <(awk '{print $1}' /tmp/repro-second.txt) && echo REPRODUCIBLE
```

输出（以实测为准）：

```text
REPRODUCIBLE
```

两个目录、两棵 tmp、相隔数小时的两次构建，ubifs 镜像逐字节相同。一处如实交代：两边**文件名**里的时间戳段并不相同——那是墙钟（镜像配方不走 SDE 命名，16.5.1 认过账），所以比对只认内容哈希；要看"连文件名都相同"的活例，kernel 的 deploy 产物才是（deploy 类产物的文件名时间戳由 SDE 推导）。可重现证明这一环，焊死了。

#### 16.7.1 坑 1：放开 license 排除门槛——先炸通配符，再连锁倒下

发作过程在 16.3.3 之后：阿凯想亲眼看看 11.7 那行注释态的 `INCOMPATIBLE_LICENSE = "*GPL-3.0*"` 放开是什么效果。取消注释，构建——没等到编译开始就炸了：

```text

```

阿凯愣了一下：bash 还没加呢，fatal 跟包没关系，落在**配方解析**上。老周路过瞟了一眼："invalid 后面跟着哪个词？"——wildcard。答案在 migration-4.0：通配符取值只放行三个特定形态——`AGPL-3.0*` / `GPL-3.0*` / `LGPL-3.0*`，都**不带前导星**（各自展开为 `-only` 加 `-or-later` 两个值）；其余含 `*` 的条目，第一个 PACKAGES 非空的 target 配方解析时直接 `bb.fatal`（oe/license.py 第 277-300 行的检查，由 base.bbclass 第 574 行的解析期调用触发）。权威写法在 ref-manual 变量术语表的 INCOMPATIBLE_LICENSE 条目；老教程里满坑满谷的 `*GPL-3.0*` 是 4.0 之前的老写法，documentation.conf 第 229 行的示例至今没跟上。**顺带自我订正一笔：11.7 留在 tiger-distro.conf 里的那行注释态示例也是老写法**——注释着不炸，一旦照抄放开就踩这个坑。

```bitbake
# 文件路径：~/workspace/meta-tiger/conf/distro/tiger-distro.conf（临时演示，改完当场还原）
INCOMPATIBLE_LICENSE = "GPL-3.0*"   # 无前导星——Scarthgap 唯一认的通配形态
```

构建——**纹丝不动，构建通过**。门槛拦不到不存在的东西：16.3 的审计早说了，今天的镜像里 GPL-3.0 族命中为零。

机理一句话：**license 排除是解析期除名，不是"装完再删"**——被排除的配方从构建里整个消失（base.bbclass 第 591 行的 SkipRecipe），依赖它的东西连锁报错。排错的第一动作是在报错里认出死因句：看到 `was skipped: it has incompatible license(s)` 就知道不是缺配方，是被门槛拦了；看到 `invalid license wildcard entry` 则更进一步——连门槛的写法本身都非法。演示完临时改动（distro conf 的门槛行、tiger-image 的 bash）**当场还原，不进提交**。

族谱认门：后半段与 7.3.1 的 UBOOT_MACHINE 未设、11.7 的 LICENSE_FLAGS 未放行同族——都是**解析期 SkipRecipe 一族**，报错都带 `was skipped:` 后缀，后缀整句就是死因；前半段的 fatal 是另一族——取值合法性检查，门槛还没轮到拦包，自己先被解析器拦下了。

#### 16.7.2 坑 2：构建时间戳混进镜像——缓存替你把坑遮住了

这个坑是阿凯自己埋的，发作在 16.5.3 验证过关、发布包组完之后——他手痒又给 tiger-sysinfo 加了个"贴心"功能，现场维护时能看出这是哪天的构建：

```bitbake
# 文件路径：~/workspace/meta-tiger/recipes-core/tiger-sysinfo/tiger-sysinfo_1.0.bb
# （错误示范，请勿模仿）
do_install:append() {
    install -d ${D}${datadir}/tiger-sysinfo
    echo "built at $(date -u '+%Y-%m-%d %H:%M:%S UTC')" > ${D}${datadir}/tiger-sysinfo/buildinfo
}
```

改完，阿凯先把会话切回主构建目录——16.5.3 最后 source 的是 build-repro，bitbake 认 BBPATH 不认 cwd——然后构建一遍，紧接着再构建一遍做比对——相同。阿凯以为没事。老周路过看了一眼："你比对那一遍，tiger-sysinfo 重新编译了吗？"

一句话点醒。**sstate 遮蔽**：任务签名里没有时间这个因子，第二遍构建 tiger-sysinfo 直接命中缓存，旧包原样端回来——两次构建"相同"是缓存的功劳，坑被遮住了。遮蔽这一族 15.6 见过另一面（externalsrc 工作区开着时，bump SRCREV 毫无变化）。逼它现形：

```bash
cd ~/workspace/poky
source oe-init-build-env ../build

# 先把当前这遍的 ipk 存证——cleansstate 重建后，deploy 里的旧包会被新包覆盖
cp tmp/deploy/ipk/cortexa53/tiger-sysinfo_1.0-r0_cortexa53.ipk /tmp/tiger-sysinfo_build1.ipk

# 清掉 tiger-sysinfo 的 sstate 条目，逼它真重建
bitbake -c cleansstate tiger-sysinfo
bitbake tiger-image

# 前后两个 ipk 并排比对（diffoscope 需 sudo apt install diffoscope）
sha256sum /tmp/tiger-sysinfo_build1.ipk tmp/deploy/ipk/cortexa53/tiger-sysinfo_1.0-r0_cortexa53.ipk
diffoscope /tmp/tiger-sysinfo_build1.ipk tmp/deploy/ipk/cortexa53/tiger-sysinfo_1.0-r0_cortexa53.ipk
```

diffoscope 的输出直指 `/usr/share/tiger-sysinfo/buildinfo` 里那行时间戳——两个包唯一的差异。

机理两句话。其一，`SOURCE_DATE_EPOCH` 只对**认这个环境变量的工具**生效（编译器、tar、内核构建脚本）；shell 里直接 `date` 拿的是墙钟，机制管不着——**可重现的最后一公里在配方作者手里**。其二，这族的阴险同样在遮蔽：不 cleansstate 就复验，缓存永远替你打掩护。老周补了一句点睛："你要肯再跑一遍 16.5.3 的双目录实验，它也藏不住——全新 sstate 里 tiger-sysinfo 必重建，两个墙钟当场打架。可发布季没人天天跑得起全量验证，所以纪律只能落在配方作者手里。"修复两选一——把 `date` 删掉（构建时间本来就有 buildhistory 记账），或者非要不可时用 `${@d.getVar('SOURCE_DATE_EPOCH')}` 注入机制认可的时间戳。阿凯选了删掉。修复后再来一轮同款逼供（存证、cleansstate、重建、比对），结果一致，收工。

> **💡 提示**：不可重现的另一常见来源是**并行编译顺序**——静态库的 `.a` 归档成员顺序随调度先后漂移。难以稳定复现，不实操；现象认得即可（两次构建的 `.a` 内容相同、成员顺序不同），diffoscope 一样抓得到。

### 16.8 本章小结

白板五件证据回顾：

- **16.1 版本固定**：SRCREV 全量审计（`^` 锚行首滤注释噪音；三个 git 直拉各占一席，QEMU 走 tarball+校验和形态）；`AUTOREV` 是发布禁忌；**层基线**——poky / meta-arm / meta-tiger 三个层自己的提交（buildhistory 的 metadata-revs 是自动底账），老周只问"poky 谁记"逼出来的一笔；patch 清单进证据链（四个 patch 的 Upstream-Status 一张表，chapter 15 的 `Pending` 第一次进发布物）；发布态切 prod 且不回切（三元组不动，翻签名的是优化档与特性族）。
- **16.2 源码归档**：清单 ≠ 归档——GPL 随附源码义务靠**源码归档类（archiver.bbclass）**兑现；默认 `patched` 模式（归档打完补丁的源码树）、copyleft 过滤器（`GPL* LGPL* AGPL*` 才归档，义务范围即归档范围）、`tmp/deploy/sources/` 按 TARGET_SYS 分目录（gcc/libgcc 不归档、gcc-source 落 allarch）；INHERIT 落 prod delta——与 13.5 buildhistory 落 base 是同一套"谁需要谁背"的两处选边。
- **16.3 license 清单**：license.manifest 自动产出（license.bbclass:262 全局挂接），四列认读、`LICENSE` 是包级取值（`LICENSE:${PN}` 可覆盖配方级）；路径段 `tiger_aarch64`（MACHINE_ARCH 下划线替换）；审计 = grep 对账 11.7 两行注释态门槛（今天 GPL-3.0 命中为零——busybox 系镜像的结构性结果，仍每版对账；grep 命中 ≠ 门槛命中，libgcc 一族的 GCC 例外认得即可）；SDK 缺口收账——目标侧已由镜像清单覆盖，SDK 的 SBOM 也早有产出。
- **16.4 SBOM**：人看的表 vs 机器看的图；**默认开启**——create-spdx 经 defaultsetup.conf 的 INHERIT_DISTRO 全局继承，从 chapter 1 起就在产出，本章动作是"发现、认识、纳入证据链"而非开启；`create-spdx` 是稳定别名，Scarthgap 指向 SPDX 2.2（3.0.1 备选，切换走 INHERIT_DISTRO 的 remove + append 两步）；产物——`tmp/deploy/spdx/2.2/<arch>/` 下 recipes/packages/runtime 三类明细文档，镜像级交付物是 deploy 里的 `.spdx.tar.zst` 全量包（索引与镜像级文档收在包内，组件文档名按 SPDX name 直落、包级不带版本号）。
- **16.5 可重现构建**：锁源 ≠ 锁构建；Scarthgap **没有开关、内建默认**（`SOURCE_DATE_EPOCH`：git 源码取末次提交时间戳，tarball 取树内最新文件时间戳）；文件名时间戳要细分——deploy 类产物（kernel/U-Boot）走 SDE，镜像走墙钟，比对认内容哈希；默认开启 ≠ 保证达成——加层即出保证范围，主线动作是"确认 + 验证"；实验设计三要点：sstate 命中不算数、另起构建目录（DL_DIR 改绝对路径共享 downloads、SSTATE_DIR 留空）、sha256 并排。
- **16.6 交付清单**：五件收拢 + 测试证据（resulttool 伏笔兑现；对照组出处如实登记进 MANIFEST）+ 可重现证明进包（repro/）；MANIFEST 落纸全部基线；整包 sha256 + tar；老周拿 OTA 三问当堂考，阿凯逐条答出——证据链叙事闭环。
- **16.7 两个坑**：坑 1 两拍——`*GPL-3.0*` 是 4.0 起废止的老写法，非法通配符解析期直接 fatal（合法形态无前导星 `GPL-3.0*`，只展开 -only/-or-later）；改对后 license 排除是解析期除名（`was skipped: it has incompatible license(s)` 是认门钥匙，SkipRecipe 族又一员）。坑 2 时间戳的阴险在 sstate 遮蔽——不 cleansstate 的复验等于没验；双目录实验抓得住它，但最后一公里靠配方作者纪律。
